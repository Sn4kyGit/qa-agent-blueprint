Installation

Am einfachsten: dem Agenten sagen. In Claude Code (im Projekt, das getestet werden soll) einfügen:

Set up https://github.com/Sn4kyGit/qa-agent-blueprint as a Claude Code
plugin in this project. Read its AGENTS.md first and follow the runbook.

Oder selbst zwei Befehle — --scope project aktiviert nur hier, ohne Flag überall:

claude plugin marketplace add Sn4kyGit/qa-agent-blueprint
claude plugin install --scope project qa-agent-blueprint@qa-agent-blueprint-marketplace

Unter opencode (modell-agnostisch, Modell = deine /models-Wahl): install.sh --mode opencode --target <projekt> --yes vom Clone aus — Details: Quickstart opencode.

Für wechselnde Claude-Code- und opencode-Sessions in derselben QA-Home: install.sh --mode shared — beide bleiben ohne Re-Onboarding startbereit, /agentswitch prüft read-only.

Ende-zu-Ende verifiziert (claude 2.1.263): registriert 30 Skills, 5 Subagents, 4 Hooks und beide MCP-Server. Solange das Repo privat ist, braucht der Fetch GitHub-Auth (gh auth login) — darunter läuft schlicht git. Alternativ: Clone + install.sh (siehe README).

Der Ablauf

Ticket→ Projekt erkannt→ Produkt erkannt→ Wissen angewendet→ getestet→ Evidence→ berichtet→ gelernt

Jede Stufe hat eine Datei als Quelle und, wo es zählt, einen Hook als Durchsetzung.

Wer am Steuer sitzt — drei Execution Modes

Seit 0.12.0 entscheidet eine Zeile in der Projektdatei, wie ein Ticket getestet wird: live per Browser (MCP) oder über ein vorher geschriebenes Skript (CLI) — oder die taktische Mischung. Jeder JIRA-Report trägt den Modus, damit klar ist, ob ein Ergebnis beobachtet oder nur assertiert wurde.

ModusWie getestet wirdKostenWann
mcp-onlyModell steuert live, jeder SchritthochNeues Projekt, explorativ, visuell, hohes Risiko
hybrid (Standard)Probe → Spec per CLI → Rotprobe → kurzer Live-CheckmittelDer Normalfall; rechnet sich ab dem ersten Retest
cli-firstNur die Suite; MCP nur bei unklarem FehlschlagniedrigGepflegte Suite, Regression, Pipeline

Vier Regeln machen den Hybridmodus ehrlich: keine blind geschriebene Spec (Recon zuerst), positive und spezifische Assertions, die Rotprobe (eine Spec, die nie rot war, beweist nichts) und der Beobachtungskanal in jedem Lauf. Eskaliert wird automatisch: visuelles Ticket, hohes Risiko, fehlende Recon oder unklarer Fehlschlag → immer live. Umstellen: Mode in PROJECT.md — bei Bestandsprojekten bietet /re-board die Sektion im Dialog an. Ausführlich (deutsch): docs/execution-modes.md.

Befehle im Überblick

Kein Auswendiglernen nötig: „Teste SHOP-1234" oder „wie läuft's mit dem Testing?" routet genauso wie der Slash-Befehl — Deutsch oder Englisch, die Befehle sind nur die explizite, garantierte Form. Im Plugin-Modus heißen sie /qa-agent-blueprint:<name>. Die komplette Liste zeigt jederzeit /qa-agent-blueprint:qa-help — auch direkt in der Session.

Drei Dinge zum Einordnen: Shadow-Modus ist standardmäßig an — JIRA-Kommentare werden komponiert, aber erst nach Freigabe gepostet. Die zehn Spezialisten-Skills (API, Accessibility, Security, Visual …) zieht qa-manager selbständig, wenn die Feature-Matrix des Produkts es vorgibt — kein Direktaufruf nötig. Und Evidence ist Pflicht: Jeder Lauf endet mit einem Verdikt und Artefakten unter evidence/.

Die fünf Ebenen

Was die Tokenkosten niedrig hält: nur Ebene 1 ist immer im Kontext, alles andere lädt bei Bedarf — oder nie.

5Evidence

Screenshots, Logs, Traces und ein maschinenlesbares Summary pro Lauf. Nie im Modellkontext — und nicht write-only: /qa-report liest sie zurück.

evidence/<KEY>/<TICKET>/<YYYYMMDD-HHMMSS>/

Was der Agent kann

Skill oder Subagent — der Unterschied ist nicht kosmetisch. Ein Skill ist eine Anleitung, die erst beim Aufruf in den Kontext geladen wird; idle kostet er nur seinen Namen und seine Beschreibung. Ein Subagent hat zusätzlich ein eigenes Kontextfenster und eine eingeschränkte Werkzeugliste — er läuft abgeschottet und gibt nur ein Ergebnis zurück. Deshalb sind alle Ausführungsrollen Subagents: ein 30-Schritte-Browser-Transkript darf den Hauptkontext nicht fluten.

Die 5 Subagents

SubagentRolleWerkzeuge
qa-manager Der Dirigent: liest das Ticket, routet zu Projekt und Produkt, entscheidet die Strategie anhand der Feature-Matrix, delegiert an die anderen — und prüft am Ende, ob Evidence und Deklaration wirklich da sind. Fährt selbst keinen Browser und schreibt keine Specs. Read, Write, Edit, Grep, Glob, Bash, Task, atlassian
test-executor Exploratives Testen und Reproduktion über Playwright MCP, isolierte Browser-Session pro Lauf. Nutzt den Accessibility-Snapshot zum Navigieren und Screenshots nur als Beweis — nicht zum „Ansehen" der Seite. playwright (MCP), Read, Write, Bash
test-automator Schreibt und fährt Specs über den CLI-Runner — rund 4× günstiger als derselbe Ablauf turn-by-turn über MCP. Arbeitet im Framework der Suite (Playwright oder WebdriverIO, inkl. Die Werkzeuglisten sind Absicht: test-executor hat keinen Zugriff auf JIRA, bug-reporter keinen auf einen Browser, failure-analyst kann nichts editieren. Wer nicht schreiben können muss, kann es nicht.

Der Kniff, der ~30 Dateiänderungen erspart hat: wo eine Regel PROJECT.md sagt, ist die effektive Projektdatei gemeint — Projektdatei, gemergt mit der gerouteten Produktdatei. Kein geroutetes Produkt heißt: nichts gemergt, Verhalten exakt wie vorher.

Routing-Leiter

StufeSignal
1Produkt explizit genannt (--product=ADMIN oder „teste das im Admin")
2Genau ein Treffer über die JIRA-Komponente
3Genau ein Treffer über ein Label (exakt, kein Beinahe-Treffer)
4Treffer auf einen project-wide-Eintrag → Infra-Ticket, nur Projektdatei
5Sekundärsignale: Epic/Parent, Fix Version, geänderte MR-Pfade
6Kein Treffer, aber ein Default deklariert → Default mit niedriger Konfidenz
7Mehrdeutig oder unbekannt → nachfragen; headless: BLOCKED

Ein Default löst Stille auf, niemals einen Konflikt — sonst testet der Agent überzeugend grün am falschen Produkt vorbei. Und das Routing lernt: eine vom Menschen formulierte Regel landet sofort in der Registry, ein Einzelfall nach der zweiten gleichartigen Auflösung, eine Ausnahme nie.

Warum es diese Fixtures gibt. Der Guard-Hook hat über die gesamte Lebenszeit des Repos nichts blockiert: die Python-Ausdrücke waren falsch gequotet, der Parser scheiterte still, jede Prüfung wurde übersprungen — und in der Review sah alles korrekt aus. Seitdem gilt: ein Hook ist erst dann Durchsetzung, wenn ein Test beweist, dass er blockt. Dieselbe Regel hat später weitere echte Fehler gefunden, darunter einen, der jeden Skill beim zweiten Installationslauf als Kollision meldete.

Shadow-Modus — standardmäßig an

Shadow-Modus ist Default: der Agent testet vollständig, erzeugt Evidence, komponiert Kommentar und Transition — und legt sie als Vorschlag ab, statt sie zu posten. Schreibzugriff wird explizit erteilt: QA_AGENT_SHADOW=0 oder Shadow mode: off im Projektfile. Prüfbar am bestehenden Audit-Log: ein Shadow-Lauf mit einem Eintrag darin ist ein Bug, keine Ermessensfrage.

Das größte Adoptionsrisiko ist nicht Technik, sondern Vertrauen. Ein Agent, der ab Tag eins in echte Tickets schreibt, wird beim ersten falschen Reopen abgeschaltet — und dann ist die Blaupause politisch tot, egal wie gut sie ist. Zwei Wochen Shadow-Betrieb sind der Nachweis, den ein Team braucht, um Schreibrechte zu vergeben.

Secrets: einmal in die Keychain, nie wieder im Chat

Schluss mit Passwort-Chaos: der Agent sieht, welche Logins er hat — statt zu fragen („du hast die Daten doch") oder sich welche auszudenken. Deklariert ein Projekt Secrets source: keychain, kommen alle Werte aus der macOS Schlüsselbundverwaltung: nie im Chat, nie in Dateien im Repo, nie auf GitHub.

🔑 Testuser-Logins

Der Resolver (resolve-secrets.sh) schreibt .env.playwright-secrets aus der Keychain — beim Onboarding, bei /re-board und wann immer die Datei fehlt. Der Session-Start zeigt eine Statuszeile (6/6 Logins vorhanden, Fehlende namentlich). Das Einrichten macht der Agent selbst: Import räumt früher handgetippte Werte aus der Env-Datei in die Keychain um, Capture fragt jedes fehlende Passwort über einen nativen macOS-Dialog ab — Eingabe verdeckt, ins Fenster getippt, nie in den Chat. Der Agent sieht zu keinem Zeitpunkt einen Wert, er meldet nur: „3 gespeichert, 1 fehlt noch."

☁️ JIRA-PAT (Data Center)

Dieselbe Mechanik eine Ebene höher: Service JIRA_PAT_<jira-host>, Account jira. Der Session-Start-Hook exportiert den Token pro Projekt in die Session ($CLAUDE_ENV_FILE) — er liegt in keiner Datei und braucht keinen globalen Export in der ~/.zshrc. CI/Nicht-macOS: JIRA_PERSONAL_TOKEN wie gehabt, der gewinnt immer.

# einmalig pro Passwort — der Service-Name ist der KOMPLETTE
# Secret-Key aus PROJECT.md → „Test users" → Spalte „Env/secret key",
# nicht nur das Projekt-Kürzel:
security add-generic-password -s SHOP_QA_STANDARD_PASSWORD -a qa -w

Rotation oder neuer Testuser? Der Agent meldet den fehlenden Key namentlich und fragt per Dialog nach. Secrets source: env-file (Handpflege) bleibt der Default — Keychain ist eine Projektentscheidung, gefragt beim Onboarding, in zwei Minuten nachgerüstet via /re-board.

Der Lernkreislauf

→Capture wird erzwungen

Jeder Lauf deklariert im Summary, was gelernt wurde — oder in einem Satz, warum nichts anfiel. Fehlt die Deklaration, blockt der Stop-Hook.

→Grooming wird sichtbar

Der Session-Start meldet die Zahl ungegroomter Einträge, damit kein Rückstau still anwächst.

→Promotion ist das Ziel

Zweimal gesehen heißt: rein in eine Regel, eine Projekt- oder Produktdatei — dort wird es automatisch geladen und nie wieder erklärt. Die Feature-Matrix wird nachgezogen: eine veraltete Matrix ist schlechter als keine, weil sie belegt aussieht. Flow-Wissen — welche Bereiche der App wie zusammenhängen — wandert in die Flow-Map (flow-map.md): /retest-bug zielt seine Regressions-Sweeps aus den dort kuratierten Nachbar-Flows, statt zu raten.

MCP-Server

Kein festes Limit, sondern ein deklariertes Register: .mcp.json ist die Verdrahtung, die Tabelle in der Regel die Begründung. Steht ein Server nur in einem von beiden, ist das ein Befund. Der Agent fügt nie selbst einen hinzu — er schlägt vor, der Mensch entscheidet.

ServerWarum im Budget
playwrightOhne Browser kein UI-Test. Läuft --isolated --headless --secrets.
atlassianTickets rein, Ergebnisse raus — die ganze Prämisse ist ticketgetrieben.

Ein CLI ist kein Server. Eine Pipeline zu triggern (gh, glab, curl) ist ein Bash-Kommando, das im Projektfile steht — kein Grund für einen dritten MCP-Server. /deploy-to-stage prüft dieses Feld vorab und meldet BLOCKED, wenn es fehlt, statt sich ein plausibel aussehendes Kommando auszudenken.

Credential-Server sind erlaubt, aber mit Auflage. Ein Vault-MCP darf eine Referenz für das Tool auflösen, das sie braucht — und nie einen Wert ins Transkript, in eine Datei, ein Ticket oder ein Artefakt bringen. Auf macOS ist dafür meist gar kein Server nötig: die Keychain-Integration (siehe oben) liefert Testuser-Logins und den JIRA-PAT, und Browser-Logins laufen weiterhin über die --secrets-Maskierung.

Was kostet der Betrieb?

Das Plugin ist kostenlos. Das Git-Repo wird genau zweimal kontaktiert: bei der Installation und beim expliziten Update. Alles andere läuft lokal; die einzigen Netzwerk-Ziele im Betrieb sind dein JIRA und deine Stage. Keine Telemetrie, keine Lizenz-Checks.

Die echten Kosten sind Modell-Tokens. Die immer geladene Ebene ist gemessen (~8.300 Tokens) und gedeckelt; Skills und Detailregeln laden bei Bedarf. Learnings werden ticketbezogen durchsucht, rohe Evidence nicht eingelesen, und einfache Tickets überspringen die Manager-Ebene. Eine versiegelte Run-Capsule ersetzt bei jedem weiteren Agenten-Spawn das erneute Lesen und Mergen des Projektkontexts. Claude Code nutzt Sonnet für die Ausführungsrollen; opencode lässt die Modellwahl bei /models.

KostentreiberGegenmaßnahme
Browser-Snapshot-Verlaufisolierter Execution-Subagent; bei Claude Code standardmäßig Sonnet
wiederholtes Intake/RoutingFast Path bzw. Manager-Handoff mit fertigen Artefakten
Tests auf altem/fehlendem BuildReadiness vor jeder Stage-Aktion
wachsende Lern- und Rohdaten16-KB-Grooming, verdichtete Promotion, Raw-Read-Denys
wiederholte Flowsvorhandene Specs über den CLI-Runner

Ehrlichkeit: Sonnet verändert den Preis der Browser-Tokens, nicht ihre Menge. Für 0.15.0 liegt kein neues Kostenbenchmark vor; ältere Euro- und Ticket-Schätzungen sind deshalb keine Zusage. Miss mit /usage und den Session-Logs.

Häufige Fragen

Die Fragen, die im Gespräch immer kommen — beantwortet ohne Fachjargon.

?Wie funktioniert das Gedächtnis?

Gar nicht im Kopf — alles liegt als normale Textdateien in deinem Projektordner, einsehbar und per Git teilbar. Fünf Schubladen: das Handbuch (immer dabei, nur die Regeln), die Fachbücher (30 Skills, laden nur bei Bedarf), die Projektakte (Umgebungen, Testuser, Runbooks — einmal eingerichtet), das Lerntagebuch (Überraschungen aus Läufen) und die Beweise (Screenshots, Logs — als Datei, nie im Gedächtnis). Der Clou: Am Ende jeder Session muss der Agent deklarieren, was er gelernt hat — ein Hook blockt das Session-Ende sonst. Was zweimal vorkam, wandert ins Handbuch und muss nie wieder erklärt werden; was verworfen wurde, landet im Rejected-Buffer und wird nicht erneut vorgeschlagen.

?Verbrennt das ständige Lesen und Lernen nicht selbst Tokens?

Ja — deshalb ist der Lernkreislauf begrenzt: Capture dedupliziert sofort, Grooming arbeitet höchstens zehn älteste Einträge pro Durchlauf und startet spätestens bei 16 KB. Promotion ersetzt und verdichtet statt anzuhängen. Beim Ticket werden nur stabile Projektdaten und passende Learning-Einträge gelesen, nicht ganze Archive. Der Nutzen ist, bekannte Umgebungen, Fallstricke und Deploy-Wege nicht bei jedem Lauf neu erkunden zu müssen; ein eigenes Benchmark für 0.15.0 steht noch aus.

?Wie effizient ist eine Session?

Die immer geladene Ebene ist ~8.300 Tokens (gemessen, per Test gedeckelt). Browser-Arbeit läuft in abgeschotteten Teil-Sessions; einfache Tickets gehen direkt an genau einen Execution-Agenten, komplexe übergeben fertiges Intake und Readiness an den Manager. Vorhandene Specs laufen über den CLI-Runner. Die Execution Modes bestimmen, wo sich teure Live-Beobachtung lohnt; gemessen wird mit /usage, nicht mit alten Schätzwerten.

?Brauche ich zwingend JIRA?

Der Blueprint ist ticketgetrieben — der Ticket-Schlüssel ist der Eingang, über den der Agent alles findet. Gelesen wird über den Atlassian-MCP-Server (Cloud oder Data Center); nutzt ein Projekt JIRA nur per Weboberfläche, geht es notfalls auch über den Browser. Ohne JIRA ergäbe das Routing keinen Sinn — aber die Skills (exploratives Testen, Accessibility, Security, Autotests) funktionieren auch ticketlos.

?Läuft das auch ohne Claude Code?

Ja — derselbe Blueprint läuft unter opencode (modell-offen, das Modell ist deine Wahl) und wird dort per Symlink-Install verdrahtet. Ein Router-Text für beide Welten, keine Drift: der Session-Start-Hook injiziert ihn im Plugin-Modus wortwörtlich. Hooks, Skills und Guardrails sind auf beiden Seiten dieselben, die Fixture-Batterie läuft für beide.

?Was passiert mit meinen Daten?

Nach der Installation läuft alles lokal. Netzwerk geht nur zu deinem JIRA und deiner Stage — keine Telemetrie, keine Lizenz-Checks, das Repo wird nur bei Install und Update angefasst. Passwörter sieht der Agent nie: Testuser-Logins und der JIRA-Token liegen im macOS-Schlüsselbund, er sieht nur „6/6 Logins vorhanden". Direkte Secret-Lesungen sind ein Opt-in, das nur ein Mensch erteilen kann.

?Was, wenn der Agent sich irrt?

Dafür gibt es eingebaute Ehrlichkeit statt Nachsicht: Bei jedem FAIL klärt ein eigener Prüfer (ohne Schreibrechte), ob das Produkt kaputt oder der Test veraltet ist. Unsicherheit wird zu NEEDS_REVIEW — ein Vorschlag an einen Menschen, kein Bug-Ticket, kein Statuswechsel. Und wenn ein Mensch den Agenten überstimmt, ist das die wertvollste Learning im ganzen System: Sie wandert mit Ursachenanalyse ins Regelwerk, damit derselbe Fehlgriff nicht zweimal passiert.

?Kann er auch in Produktion testen?

Nein — niemals, egal wer fragt oder wie es formuliert ist. Nur Stage. Verlangt ein Ticket eine Prod-Verifizierung, meldet der Agent BLOCKED mit Grund, statt kreativ zu werden. Deploys darf er nur auf Stage und nur, wenn das Projekt es ausdrücklich erlaubt; MRs kommentieren oder mergen darf er nie.

?Muss ich programmieren können oder Befehle kennen?

Nein. Du schreibst ganz normal: „Teste SHOP-1234", „Der Fix ist auf Stage, prüf das", „Wie läuft's mit dem Testing?" — deutsch oder englisch. Auch das Lernen läuft von allein: Jede Session muss deklarieren, was sie gelernt hat (ein Hook erzwingt es), und wächst der Stapel ungeprüfter Learnings über eine Schwelle (5 Einträge, 14 Tage alt oder 16 KB), räumt der Agent ihn am Session-Ende von selbst auf und berichtet in einem Satz, was daraus wurde. Die Einrichtung ist ein geführtes Interview (~30–60 Minuten pro Projekt). Einzige Menschen-Aufgaben: JIRA-Zugang einrichten, Testuser-Passwörter einmal in den Schlüsselbund legen, und am Anfang die Shadow-Modus-Vorschläge prüfen, bis du ihm Schreibrechte gibst.

?Wie fange ich an?

Zwei Befehle (siehe Installation oben), Claude Code neu starten, JIRA einmal per OAuth verbinden — dann /onboard-project und das Interview beantworten. Danach heißt es nur noch: „Teste TICKET." Der Shadow-Modus ist ab Tag eins an — der Agent testet vollständig, postet aber nichts, bis du es freigibst.
