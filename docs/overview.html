The flow

Ticket→ Project identified→ Product identified→ Knowledge applied→ tested→ Evidence→ reported→ learned

Every stage has a file as its source and, where it counts, a hook as enforcement.

Who's at the wheel — three execution modes

Since 0.12.0 one line in the project file decides how a ticket is tested: live via browser (MCP) or through a pre-written script (CLI) — or the tactical mix. Every JIRA report carries the mode, so it is clear whether a result was observed or merely asserted.

ModeHow it's testedCostWhen
mcp-onlyModel drives live, every stephighNew project, exploratory, visual, high risk
hybrid (default)Probe → spec via CLI → red probe → short live checkmediumThe everyday case; pays off from the first retest
cli-firstThe suite only; MCP only on unclear failureslowMaintained suite, regression, pipeline

Four rules keep hybrid mode honest: no blindly written spec (recon first), positive and specific assertions, the red probe (a spec that was never red proves nothing) and the observation channel in every run. Escalation is automatic: visual ticket, high risk, missing recon or unclear failure → always live. Switch it: Mode in PROJECT.md — for existing projects /re-board offers the section in dialog. Full write-up (in German): docs/execution-modes.md.

The Five Layers

What keeps the token budget low: only layer 1 is always in context, everything else loads on demand — or never.

1Global core — just the norms

Router plus five rule files: everything that must bind before any skill is loaded. The detail behind it lives in docs/rules/ and is read when its topic comes up — each file names its trigger at the top.

CLAUDE.md + .claude/rules/core/ · measured 7,040 tokens, budget 8,400

2Skills & Subagents

Loaded only on demand. Subagents have their own context windows, so a 30-step browser transcript never lands in the main context — only a verdict comes back.

.claude/skills/ · .claude/agents/

3Project and product context

Only the active project is read. If a JIRA project covers several products, exactly one short product file is added — one that lists only the deltas.

projects/<KEY>/ → products/<PRODUCT>/

4Learning system

Inbox as the catch-all, topic files as the condensed middle, promotion into rules and project/product files as the destination. Knowledge only counts once it arrives there.

memory/INDEX.md · memory/learnings/

5Evidence

Screenshots, logs, traces and a machine-readable summary per run. Never in the model context — and not write-only: /qa-report reads them back.

evidence/<KEY>/<TICKET>/<YYYYMMDD-HHMMSS>/

What the agent can do

Skill or subagent — the difference is not cosmetic. A skill is an instruction set that only loads into context when invoked; idle it costs just its name and its description. A subagent additionally has its own context window and a restricted tool list — it runs sandboxed and returns only a result. That is why all execution roles are subagents: a 30-step browser transcript must not flood the main context.

Knowledge architecture

# Project-wide knowledge at the top, deltas at the bottom
projects/SHOP/
├── PROJECT.md              ← applies to ALL products, holds the routing registry
├── learnings.md
├── flow-map.md             ← curated by /retro-learn: flows, anchors, neighbors
├── templates/bug-report.md
└── products/               ← completely absent in single-product projects
    ├── STOREFRONT/           ← lists ONLY what differs (~60 lines)
    └── ADMIN/

The trick that saved ~30 file changes: wherever a rule says PROJECT.md, it means the effective project file — the project file merged with the routed product file. No routed product means: nothing merged, behavior exactly as before.

Routing ladder

StepSignal
1Product named explicitly (--product=ADMIN or “test that in the admin”)
2Exactly one match via the JIRA component
3Exactly one match via a label (exact, no near match)
4Match on a project-wide entry → infra ticket, project file only
5Secondary signals: epic/parent, fix version, changed MR paths
6No match, but a default declared → default with low confidence
7Ambiguous or unknown → ask; headless: BLOCKED

A default resolves silence, never a conflict — otherwise the agent confidently tests green on the wrong product. And the routing learns: a rule phrased by a human lands in the registry immediately, a one-off after its second identical resolution, an exception never.

What a product may override

AreaOverride
Environments, test users, test assets, feature matrix, gotchas, bug template, deploy stepsyes

The two most dangerous are solved structurally rather than monitored: deploy-to-stage and report-to-jira read deploy permission and transitions exclusively from the project file. No product file can grant them — no matter what a merge produces.

What is mechanically enforced

The most important part, because rules are advisory and hooks are not.

Why these fixtures exist. For the repo's entire lifetime the guard hook blocked nothing: the Python expressions were misquoted, the parser failed silently, every check was skipped — and in review everything looked correct. Since then the rule is: a hook is only enforcement once a test proves it blocks. The same rule later found more real bugs, including one that reported every skill as a collision on the second install run.

Shadow mode — on by default

Shadow mode is the default: the agent tests fully, produces evidence, composes comment and transition — and files them as a proposal instead of posting. Write access is granted explicitly: QA_AGENT_SHADOW=0 or Shadow mode: off in the project file. Verifiable against the existing audit log: a shadow run with an entry in it is a bug, not a matter of discretion.

The biggest adoption risk is not technology but trust. An agent that writes into real tickets from day one gets switched off at the first wrong reopen — and then the blueprint is politically dead, no matter how good it is. Two weeks of shadow operation are the proof a team needs before handing out write access.

Secrets: into the keychain once, never in the chat again

No more password chaos: the agent sees which logins it has — instead of asking (“you have the credentials, don't you?”) or making them up. When a project declares Secrets source: keychain, all values come from the macOS keychain: never in the chat, never in files in the repo, never on GitHub.

🔑 Test user logins

The resolver (resolve-secrets.sh) writes .env.playwright-secrets from the keychain — at onboarding, at /re-board and whenever the file is missing. Session start shows a status line (6/6 logins present, missing ones by name). The agent sets this up itself: Import moves previously hand-typed values out of the env file into the keychain, Capture prompts for each missing password via a native macOS dialog — input hidden, typed into the window, never into the chat. The agent never sees a value at any point, it only reports: “3 saved, 1 still missing.”

☁️ JIRA PAT (Data Center)

The same mechanism one level up: service JIRA_PAT_<jira-host>, account jira. The session-start hook exports the token per project into the session ($CLAUDE_ENV_FILE) — it lives in no file and needs no global export in ~/.zshrc. CI/non-macOS: JIRA_PERSONAL_TOKEN as always, which always wins.

# once per password — the service name is the COMPLETE
# secret key from PROJECT.md → “Test users” → column “Env/secret key”,
# not just the project prefix:
security add-generic-password -s SHOP_QA_STANDARD_PASSWORD -a qa -w

Rotation or a new test user? The agent reports the missing key by name and prompts via dialog. Secrets source: env-file (manual care) remains the default — keychain is a per-project decision, asked at onboarding, retrofitted in two minutes via /re-board.

The learning loop

→Capture is enforced

Every run declares in its summary what was learned — or in one sentence why nothing came up. If the declaration is missing, the stop hook blocks.

→Grooming is visible

Session start reports the number of ungroomed entries so no backlog grows silently.

→Promotion is the goal

Seen twice means: into a rule, a project or product file — there it is loaded automatically and never explained again. The feature matrix is refreshed too: an outdated matrix is worse than none, because it looks proven. Flow knowledge — which areas of the app connect how — moves into the flow map (flow-map.md): /retest-bug aims its regression sweeps at the neighboring flows curated there, instead of guessing.

MCP servers

Not a fixed limit but a declared register: .mcp.json is the wiring, the table in the rule the rationale. If a server appears in only one of the two, that is a finding. The agent never adds one itself — it proposes, the human decides.

ServerWhy it's in the budget
playwrightNo UI testing without a browser. Runs --isolated --headless --secrets.
atlassianTickets in, results out — the whole premise is ticket-driven.

A CLI is not a server. Triggering a pipeline (gh, glab, curl) is a bash command that lives in the project file — no reason for a third MCP server. /deploy-to-stage checks this field up front and reports BLOCKED when it is missing, instead of inventing a plausible-looking command.

Credential servers are allowed, but with conditions. A vault MCP may resolve a reference for the tool that needs it — and must never bring a value into the transcript, a file, a ticket or an artifact. On macOS no server is usually needed at all: the keychain integration (see above) supplies test user logins and the JIRA PAT, and browser logins continue to run through the --secrets masking.

What does running it cost?

The plugin is free. The git repo is contacted exactly twice: at installation and at an explicit update. Everything else runs locally; the only network targets in operation are your JIRA and your stage. No telemetry, no license checks.

The real cost is model tokens. The always-loaded layer is measured (~7,040 tokens) and capped; skills and detail rules load on demand. Learnings are searched per ticket, raw evidence is never read in, and simple tickets skip the manager layer. A sealed run capsule replaces re-reading and re-merging the project context at every further agent spawn. The model lane is chosen per branch: fast/low → cheap, complex low/medium → standard, high/escalated → deep. Claude maps this onto haiku/sonnet/opus; opencode inherits without overrides or uses the models and variants configured under /model-setup.

Cost driverCountermeasure
Browser snapshot historyisolated execution subagent; model lane by risk (haiku/sonnet/opus or consumer override)
repeated intake/routingfast path, or manager handoff with finished artifacts
tests on an old/missing buildreadiness before every stage action
growing learning and raw data16 KB grooming, condensed promotion, raw-read denies
repeated flowsexisting specs via the CLI runner

Honesty: the model lane changes the price of the browser tokens, not their volume. For 0.19.0 there is no new cost benchmark; older euro and per-ticket estimates are therefore not a promise. Measure with /usage and the session logs.

FAQ

The questions that always come up in conversation — answered without jargon.

?How does the memory work?

Not in anyone's head — everything lives as plain text files in your project folder, inspectable and shareable via git. Five drawers: the handbook (always with you, just the rules), the reference skills (33 skills, load only on demand), the project dossier (environments, test users, runbooks — set up once), the learning journal (surprises from runs) and the evidence (screenshots, logs — as files, never in memory). The trick: at the end of every session the agent must declare what it learned — a hook blocks the session end otherwise. Anything that came up twice moves into the handbook and never needs explaining again; what was rejected lands in the rejected buffer and is not proposed again.

?Doesn't all that constant reading and learning burn tokens itself?

Yes — which is why the learning loop is bounded: capture dedupes immediately, grooming works on at most the ten oldest entries per pass and starts at 16 KB at the latest. Promotion replaces and condenses instead of appending. For a ticket only stable project data and matching learning entries are read, never whole archives. The payoff is not having to rediscover known environments, pitfalls and deploy paths on every run; a dedicated benchmark for 0.19.0 is still pending.

?How efficient is a session?

The always-loaded layer is ~7,040 tokens (measured, capped by test). Browser work runs in sandboxed sub-sessions; simple tickets go straight to exactly one execution agent, complex ones hand finished intake and readiness to the manager. Existing specs run via the CLI runner. The execution modes determine where expensive live observation pays off; measurement comes from /usage, not old estimates.

?Do I absolutely need JIRA?

The blueprint is ticket-driven — the ticket key is the entry point through which the agent finds everything. Reading happens via the Atlassian MCP server (Cloud or Data Center); if a project uses JIRA only through the web UI, the browser works in a pinch. Without JIRA the routing would make no sense — but the skills (exploratory testing, accessibility, security, automated tests) also work without tickets.

?Does it run without Claude Code too?

Yes — the same blueprint runs under opencode (model-open, the model is your choice) and is wired up there via a symlink install. One router text for both worlds, no drift: the session-start hook injects it verbatim in plugin mode. Hooks, skills and guardrails are the same on both sides, the fixture battery runs for both.

?What happens to my data?

After installation everything runs locally. Network traffic goes only to your JIRA and your stage — no telemetry, no license checks, the repo is only touched at install and update. The agent never sees passwords: test user logins and the JIRA token live in the macOS keychain, it only sees “6/6 logins present”. Direct secret reads are an opt-in that only a human can grant.

?What if the agent is wrong?

That is what built-in honesty is for instead of leniency: on every FAIL a dedicated checker (without write access) determines whether the product is broken or the test is outdated. Uncertainty becomes NEEDS_REVIEW — a proposal to a human, no bug ticket, no status change. And when a human overrules the agent, that is the most valuable learning in the whole system: it moves with a root-cause analysis into the rulebook so the same misstep does not happen twice.

?Can it test in production too?

No — never, no matter who asks or how it is phrased. Stage only. If a ticket demands prod verification, the agent reports BLOCKED with a reason instead of getting creative. It may only deploy to stage and only when the project explicitly allows it; commenting on or merging MRs it may never do.

?Do I need to be able to program or know commands?

No. You just write normally: “Test SHOP-1234”, “The fix is on stage, check it”, “How's testing going?” — German or English. Learning runs on its own too: every session must declare what it learned (a hook enforces it), and once the stack of unchecked learnings grows past a threshold (5 entries, 14 days old or 16 KB), the agent tidies it up on its own at session end and reports in one sentence what came of it. Setup is a guided interview (~30–60 minutes per project). The only human tasks: set up JIRA access, put the test user passwords into the keychain once, and at first review the shadow-mode proposals until you grant it write access.

?How do I get started?

Two commands (see Installation above), restart Claude Code, connect JIRA once via OAuth — then /onboard-project and answer the interview. After that it is just: “Test TICKET.” Shadow mode is on from day one — the agent tests fully but posts nothing until you approve it.
