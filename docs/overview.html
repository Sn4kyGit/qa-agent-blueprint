The flow

Ticket→ Project routed→ Product routed→ Readiness gate→ Tested→ Evidence→ Judged→ Reported→ Learned

Every stage has a file as its source and, where it counts, a hook as enforcement. Nothing important is left to “the agent will probably remember”.

Why it's different

1It knows your projects

Test users as vault references, environments, deploy runbook, report format — read from PROJECT.md, not guessed. Multi-product? Each product file states only what differs.

2Evidence is mandatory

No verdict without artifacts. A Stop hook blocks the session end otherwise. Schema-v2 summaries, screenshots, hashed artifacts.

3It judges itself

An adversarial verdict court (prosecutor, defender, independent judge) reviews every verdict against OEV before it is reported. Catches the hollow PASS a validator can't.

4Learning is enforced

Every run declares what it learned. Seen twice → promoted into a rule or project file. “Explain once, never again.”

5Token-efficient by design

~8.4k always-loaded budget, on-demand skills, browser transcripts stay in subagents, a sealed capsule avoids re-merging context.

6Security-audited

Guard blocks secrets, destructive commands, self-escalation. Shadow mode by default. 30 fixture suites prove it blocks.

Architecture

How it works

Five layers, three execution modes, one quality principle (OEV), and a learning loop that is enforced — not suggested.

The five layers

Only layer 1 is always in context; everything else loads on demand — or never. That is what keeps the token budget low.

1Global core — just the norms

Router + five rule files: everything that must bind before any skill loads. Detail lives in docs/rules/, read when its topic comes up.

CLAUDE.md + .claude/rules/core/ · budget 8,400 tokens

2Skills & subagents

Loaded on demand. Subagents have their own context windows — a 30-step browser transcript never lands in the main context, only a verdict comes back.

.claude/skills/ · .claude/agents/

3Project & product context

Only the active project is read. Multi-product projects add one short product file listing only the deltas.

projects/<KEY>/ → products/<PRODUCT>/

4Learning system

Inbox → topic files → promotion into rules and project files. Knowledge only counts once it arrives there.

memory/INDEX.md · memory/learnings/

5Evidence

Screenshots, logs, traces, a machine-readable summary per run. Never in the model context — and read back by /qa-report and the rollup.

evidence/<KEY>/<TICKET>/<ts>/

Three execution modes — who's at the wheel

ModeHow it testsCostWhen
mcp-onlyModel drives the browser live, every stephighNew project, exploratory, visual, high risk
hybrid (default)Probe → spec via CLI → red probe → short live checkmediumThe everyday case; pays off from the first retest
cli-firstThe suite only; MCP on unclear failureslowMaintained suite, regression, pipeline

Four rules keep hybrid honest: no blindly written spec (recon first), positive specific assertions, the red check (a spec that was never red proves nothing), and an observation channel in every run. Escalation (visual, high risk, missing recon, unclear failure) always raises to live observation.

OEV — the quality principle

Everything the blueprint produces should be Observable, Executable, Verifiable — not just plausible.

👁 Observable

Can we see what happened? Logs, traces, screenshots, UI state, API responses. → the evidence policy.

⚙️ Executable

Was the expectation actually run? Automated specs, API tests, the red check. → execution modes + recon.

✅ Verifiable

Can we prove correctness objectively? Assertions bound to ACs, schema validation. → the verdict court.

The verdict court applies these three questions to every verdict — and is itself grounded in cited evidence (no fabrication). See the Verdict Court tab.

The learning loop

→Capture is enforced

Every run declares what it learned — or why nothing came up. Missing declaration → the Stop hook blocks.

→Grooming is visible

Session start reports ungroomed entries; past a threshold the agent tidies up on its own.

→Promotion is the goal

Seen twice → into a rule or project file, loaded automatically, never explained again. Flow knowledge moves into flow-map.md, which /retest-bug uses for regression sweeps.

Knowledge architecture & routing

projects/SHOP/

├── learnings.md

├── templates/bug-report.md

Wherever a rule says PROJECT.md, it means the effective project file — merged with the routed product file. Routing ladder: explicit → component → label → project-wide → secondary signals → default → ask. A default resolves silence, never a conflict; headless ambiguity is BLOCKED, not a guess.

Feature · v0.26–0.28

⚖️ The Verdict Court judges, not guards

A mechanically valid PASS can still be semantically hollow. Three independent read-only judges review every verdict against the evidence before it is reported.

Use case A test goes green because a negative assertion toHaveCount(0) matches nothing — the error class was simply renamed. The schema validator passes (coverage complete, hashes match). Without a judge, this hollow PASS ships to JIRA. The court catches it: unsupported → NEEDS_REVIEW, a human decides.

The trio

🗡verdict-prosecutor

Attacks the verdict: argues why it is unsupported. Hunts OEV gaps — missing artifacts, unexecuted claims, false-green negative assertions, ACs flattened in translation. Every attack cites evidence.

🛡verdict-defender

Defends the verdict: cites the artifact, the executed run/red-check, and the meaningful assertion per AC. Rebuts attacks with citations — and concedes what the evidence does not support.

⚖️verdict-judge (adjudicator)

A fresh independent context — neither the strategy-choosing orchestrator nor the executor. Weighs both briefs against the mechanical evidence (verifying citations against the actual files) and renders supported / unsupported / needs-human.

All three are read-only: no Write/Edit, no browser, no JIRA write, no delegation. Separation of powers — what must not write cannot write.

Example

# AC2: "the user gets an understandable error message"
# the spec only asserts:
expect(errorBox).toBeVisible()   ← flattened: existence, not understandability

# prosecutor: "AC2 attack — toBeVisible() does not verify the message" (cited)
# defender:   cannot rebut → concedes AC2
# judge:      cited, undefended gap → unsupported
judge-review.json → judge_verdict: "unsupported" → NEEDS_REVIEW (not PASS)

Grounding rule — OEV applies to the judges too

A judge is an LLM and can fabricate too. So every claim must cite a concrete evidence location (artifact path, assertion/TC-ID, AC number). No invented figures, no “I ran the script” when it didn't. The mechanical validator stays the backstop for “did something happen”; the judges argue “is it meaningful”. The court complements the gate, never replaces it.

Lanes: the full court runs on the complex path / high-risk; Fast Path low-risk may skip it (judge_skipped recorded, never silent). Configure judge models via /model-setup --judge — ideally a strong, different model than the executor.

Feature · v0.23

🗂️ Evidence & Retention

No verdict without artifacts — and the artifacts don't grow forever. Cleanup is notification-first and human-only: the agent never deletes evidence.

The five verdicts

VerdictMeaningConsequence
PASSTested, no findings, court-supportedComment + transition + screenshot
FAILA finding; failure-analysis supplied the classBug on product-defect; transition per class
BLOCKEDNever ran: env gone, fix not deployed, routing unresolvedReason + unblocker; not in pass rate
NEEDS_REVIEWTest probably outdated, or court found it hollowProposal to a human, no transition
NO_TESTTooling ran, no test completedOne-sentence reason, no JIRA post

Retention — two stages, human-only prune

Use case evidence/ has grown to tens of GB over months. You want it cleaned — but never by an agent that might delete the wrong run. The agent plans and notifies (“bitte aufräumen”); you run the prune command. The guard mechanically blocks any agent prune attempt.

AArtifacts (30 days)

Heavy screenshots/logs/traces go; the curated JSON/MD verdict records stay, plus a .retention.json marker.

BWhole runs (365 days)

A compact fact line is indexed before deletion — metric history survives. Minimum 90 days (the sightings window).

Protection rules: newest run per ticket, fresh runs, pending shadow proposals, NEEDS_REVIEW awaiting a ruling, .retain pins, and .audit/ are never pruned. Missing/malformed summaries fail open (kept).

Example

# the agent plans (writes nothing) and hands you the command:
python3 .claude/scripts/evidence-retention.py plan --qa-home .
#   run-prune  SHOP/SHOP-101/20240101-120000  age=651d
#   artifacts  SHOP/SHOP-101/20260815-101500  age=100d
#   protected  SHOP/SHOP-104/...  protected:ruling

# YOU run the prune in your own terminal (the agent is blocked from this):
python3 .claude/scripts/evidence-retention.py prune --qa-home . --yes

Per-project policy in PROJECT.md → ## Evidence retention. A session-start hint appears when prunable evidence crosses a threshold.

Feature · v0.24

📊 Epic / Release Rollup

“Is epic X / release Y tested well enough to ship?” — answered from existing evidence + JIRA structure. A report, not a run; it never invents a verdict for an untested child.

Use case A release manager asks “can we ship 2.14.0?”. Instead of manually collecting ticket verdicts, /rollup aggregates every child's newest evidence — and flags the trap: a child that passed on an old build is stale, not ready. A PASS on build 1.0 is not a PASS for a release shipping 2.0.

Honest classification

ClassMeaning
tested-pass / tested-failNewest evidence is a current PASS / FAIL
blocked / needs-reviewNewest evidence BLOCKED / awaiting a ruling
untestedNo evidence ever — a gap, never an invented verdict
staleEvidence predates the current build
no-testNewest run was NO_TEST — nothing tested

Flags: legacy-evidence (v1 summary), pruned-evidence (only a retention-index line survives), build-unverified. Worst verdict wins; coverage = currently-covered children / total; gates → recommendation: go | no-go | insufficient-evidence. The human decides via release-readiness.

Example

# agent fetches children (one JQL), probes the current build, then:
python3 .claude/scripts/epic-rollup.py --children children.json \
  --qa-home . --project SHOP --current-build 2.0

recommendation: no-go
  tested-pass  SHOP-901 (build 2.0)
  stale        SHOP-902 (PASS on build 1.0)   ← not ready
  untested     SHOP-903                        ← a gap
  tested-fail  SHOP-904 (P1 finding)

Output rollup.json + rollup.md in evidence/<KEY>/_rollups/ — not a run dir, no execution_summary.json. Shadow mode applies: the epic comment is a proposal, no transition. --release-mode groups by fixVersion.

Feature · v0.25 / 0.28

🎫 Stage Coordination

Parallel sessions on a shared stage stop contaminating each other. Solo users see zero change — coordination is opt-in, never forced.

Use case Two engineers test the same shared stage. One triggers a deploy while the other's test is mid-flight — the result is garbage. With coordination, the deploy holds an exclusive lease; the other run's readiness gate sees the stage is busy and reports BLOCKED with the holder info, instead of testing against a deploying stage.

Adaptive: solo by default, team opt-in

PROJECT.mdBehavior
No ## Stage coordinationsolo acquire exits 4, no leases, zero friction
Shared stage: yesteam exclusive-op leases + namespacing; readiness check 5
+ Write lease: requiredexplicit full serialization — a deliberate team choice, never a default

Namespacing is the cheap parallel path: runs create entities under qa-<runid>-… and coexist without locks. Leases are for what can't be namespaced: deploy, global reset, cache flush, feature flags.

Conflict matrix & example

deploy conflicts with everything; reset with write/data; stage-write with stage-write; data:<ns> only the same namespace. TTL + heartbeat are the crash safety net; waiting happens inside one process (no agent sleep-polling).

python3 .claude/scripts/stage-lease.py acquire --qa-home . --project SHOP \
  --env stage --scope deploy --holder anna@host --ticket SHOP-123 --wait 120
# exit 0 acquired | 3 busy (holder + expiry) | 4 coordination off (solo)

# session-start shows active leases (both harnesses):
Stage leases active: deploy on stage by anna@host (SHOP-123)

Local backend (evidence/.leases/) coordinates sessions sharing a QA home. Audit in lease.log. shared-path (team share) and api backends are future phases for cross-machine teams.

Trust & installation

🔒 Security & Setup

Rules are advisory; hooks are not. Everything important is mechanically enforced — and proven by fixtures.

What is mechanically enforced

MechanismEnforces
pre-tool-guardNo writes to .env*/secret paths, no rm -rf, no force-push; secret reads are a human opt-in; agent edits to the guard config refused; human-only files (rules/skills/hooks/PROJECT.md) protected
stop-evidence-checkNo verdict without execution_summary.json + declared learnings; machine-readable markers for pipelines
session-startOrientation, secrets status, MCP contract scan, retention + lease hints; injects the router verbatim in plugin mode
post-jira-auditEvery JIRA write lands in the audit log, headless too
context-budgetThe always-loaded layer stays within budget — measured, not asserted
Why fixtures exist. For the repo's early life the guard blocked nothing — misquoted Python, a silently failing parser, every check skipped, and review looked fine. Since then: a hook is only enforcement once a test proves it blocks. 30 suites, 200 bun tests, 67 eval cases.

Shadow mode & secrets

🌑 Shadow mode (default on)

The agent tests fully, composes comment + transition, files them as a proposal — posts nothing. Unlock: QA_AGENT_SHADOW=0 or Shadow mode: off in the project file. A shadow run with an audit-log entry is a bug.

🔑 Keychain secrets

Test-user logins + JIRA PAT live in the macOS keychain — never in chat, files, or GitHub. The agent sees “6/6 logins present”, never a value. Capture via a native hidden-input dialog; qa-secrets.mjs injects value-free into runners/MCP.

# once per password — service name = the full secret key from PROJECT.md:
security add-generic-password -s SHOP_QA_STANDARD_PASSWORD -a qa -w

Models & cost

The blueprint pins no model (model-agnostic). Lanes are consumer-owned via /model-setup: cheap/standard/deep for execution, optional --judge for the court. Claude maps lanes to haiku/sonnet/opus; opencode inherits or uses your overrides.

Cost driverCountermeasure
Browser snapshot historyIsolated execution subagent; model lane by risk
Repeated intake/routingFast path, or a sealed capsule handoff
Tests on an old/missing buildReadiness gate before every stage action
Growing evidenceRetention (human-only) + raw-read denies

No telemetry, no license checks. The repo is contacted only at install/update; in operation the only network targets are your JIRA and your stage. OpenRouter free models are a cost option for cheap/smoke — not for the judge or deep lane (capability).

FAQ

?Do I need JIRA?

The blueprint is ticket-driven — the key is the entry point. Reading via Atlassian MCP (Cloud/DC) or the browser UI. The testing skills also work without tickets.

?Does it run without Claude Code?

Yes — the same blueprint runs under opencode (model-open). One router text, same hooks/skills/guardrails, fixture battery for both.

?What if the agent is wrong?

Built-in honesty: failure-analyst (no write access) classifies every FAIL; the verdict court reviews every verdict; uncertainty → NEEDS_REVIEW. A human overruling the agent is the most valuable learning — it moves into the rulebook with a root-cause analysis.

?Can it test production?

No — never, stage only. A ticket demanding prod verification → BLOCKED with a reason. It may deploy to stage only when the project allows; never merge or approve MRs.

?Do I need to know commands?

No. Write normally: “Test SHOP-1234”, “the fix is on stage”, “how's testing going?” — German or English. Learning runs on its own. Setup is a guided interview; the only human tasks are JIRA access, keychain passwords once, and reviewing shadow proposals.
