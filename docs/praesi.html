Ausgangslage

Wer verifiziert den KI-Code?

Coding-Agenten liefern Code immer schneller. Die Prüfung hält nicht Schritt.

Tempo steigt

  • Agenten schreiben Features in Minuten statt Tagen.
  • Reviews und Tests werden zum Flaschenhals.

„AI Testing" bleibt unstrukturiert

  • Chatbot sagt „Sieht gut aus" — ohne Beweis, dass getestet wurde.
  • Keine standardisierten Reports, kein nachvollziehbares Verdict.

Kein Lernen

  • Gleiche Stolperfallen werden jede Session neu erklärt.
  • Wissen landet im Chat-Verlauf, nicht im Team.
Risiko: Ungeprüfter Code durchbricht die Pipeline — und niemand kann hinterher sagen, was eigentlich getestet wurde.
QA Agent Blueprint02 · Problem
Anschluss an den Alltag des Teams fragen: „Wer von euch hat schon mal einen KI-generierten Fix gemerged, ohne ihn wirklich zu prüfen?" Drei Karten = drei Lücken: Beweis, Standard, Lernen. Der Blueprint adressiert alle drei mechanisch.

Architektur

Fünf Schichten — Progressive Disclosure

Nur Normen sind immer geladen; alles andere kommt bei Bedarf in den Kontext. Das hält das Token-Budget klein.
LAYER 1Global CoreRouter + QA-Normen (Evidence, Security, Token-Disziplin) — immer geladen, ~7k Tokens
LAYER 2Skills & Subagentenbei Bedarf geladen — im Idle kostet ein Skill nur ~100 Tokens
LAYER 3ProjektkontextPROJECT.md / PRODUCT.md pro Kunde: Testuser, Umgebungen, Report-Format, Flow-Map
LAYER 4Learning-Systemmemory/learnings — wächst, wird konsolidiert und in Layer 1–3 promotet
LAYER 5Evidencenie im Kontext, nur referenziert: evidence/<KEY>/<TICKET>/<Zeitstempel>/
Warum das zählt: Subagenten haben eigene Kontextfenster — ein 30-Schritte-Browser-Transkript bleibt im Tester, zurück kommt ein Verdict von ≤ 40 Zeilen.

Spotlight 1

Der QA-Manager — orchestriert, testet nie selbst

Bekommt fertigen Kontext

  • Intake, Routing und Readiness (Status, Blocker, MR merged, Build deployed) erledigt der Haupt-Orchestrator vorab.
  • Ergebnis: versiegelte context-capsule.json mit Source-Hashes.
  • Der Manager liest die Capsule — er merged Projektkontext nie doppelt.

Entscheidet & delegiert

  • Teststrategie: Re-Test (Bug) oder Full-Test (Story), Execution Mode, Eskalation.
  • Wählt pro Execution-Branch die Modell-Lane und den Executor/Automator.
  • Fast Path: einfaches, risikoarmes Ticket geht direkt an einen cheap-Agenten — ohne Manager-Overhead.

Prüft die harten Regeln

  • Evidence vorhanden und validiert?
  • Security-Regeln eingehalten?
  • Report-Format des Projekts getroffen?
  • Erst dann gilt das Ticket als fertig.
Merksatz: Der Manager macht sich nie selbst die Hände schmutzig — kein Browser, keine Specs. Sonst wäre er befangen wie ein Tester, der sein eigenes Urteil reviewed.
QA Agent Blueprint06 · QA-Manager
Häufiges Missverständnis ausräumen: Readiness passiert vor dem Manager (Haupt-Orchestrator), der Manager konsumiert die Capsule. Warum? Token-Disziplin und Unveränderlichkeit: jeder Agent sieht exakt denselben geprüften Kontext, nachprüfbar über Hashes.
Spotlight 2 · Execution

Execution: explorativ live oder deterministisch per CLI

Zwei Rollen, je drei Modell-Lanes — beide liefern ein kompaktes Verdict plus Evidence, nie das Roh-Transkript.

test-executor

  • Exploratives Testen & Bug-Reproduktion via Playwright MCP in isolierter Browser-Session.
  • Chartierte SBTM-Sessions, erste Looks auf neue Features, Repro ohne wiederholbaren Spec.
  • Das 30-Schritte-Browser-Transkript bleibt in seinem Kontextfenster.

test-automator

  • Schreibt und fährt deterministische Specs (Playwright/WDIO) über den CLI-Runner.
  • Regression, wiederholbare Checks, Nightly-Suites — ~4× günstiger als derselbe Flow im MCP-Loop.
  • Red-Check beweist: der Spec kann auch rot werden.

Gemeinsame Disziplin

  • Evidence pro Schritt: Screenshots, Logs, Run-JSON.
  • Recon liefert echte Selektoren, bevor Specs blind entstehen.
  • Eskalation auf Live-Beobachtung bei visuellem Ticket, hohem Risiko, unklarer Assertion.
  • Zurück an den Orchestrator: ein Verdict von ≤ 40 Zeilen.
Merksatz: Wiederholbar? → Automator. Neu oder unklar? → Executor. Welches Modell-Budget die Rolle bekommt, entscheidet separat die Lane (Slide 10).
QA Agent Blueprint07 · Execution
Die zwei Rollen sind die Hände des Systems: Executor für alles Unklare, Automator für alles Wiederholbare. Beide existieren in cheap/standard/deep — die Lane ist eine Budget-Entscheidung, keine Rollen-Entscheidung. Red-Check erwähnen: ein Spec, der nie rot war, beweist nichts (OEV Executable).
Spotlight 3 · Analysis

Analysis: erst verstehen, dann melden

failure-analyst und bug-reporter trennen echte Defekte von Test-Schuld — bevor ein Ticket entsteht.

failure-analyst

  • Läuft bei JEDEM FAIL, vor jedem Bug.
  • Vergleicht die fehlgeschlagene Assertion mit dem JIRA-Change-Record und dem Versionsfenster seit dem letzten Pass.
  • Klassifiziert: product-defect · test-outdated · test-brittle · environment · flake · undetermined.

bug-reporter

  • Nur bei product-defect / undetermined.
  • Bug-Ticket strikt nach Projekt-Template: Severity/Priority-Mapping, Evidence-Referenzen.
  • Transition „Reopen" — kein Freitext-Bug, kein Ticket ohne Belege.

Was nie passiert

  • Test-Änderungen werden nur vorgeschlagen, nie angewendet.
  • Veralteter/brittler Test → NEEDS_REVIEW statt Bug.
  • Environment → BLOCKED · Flake → test-reliability.
  • Keine endlose Reopen-Schleife in JIRA.
Merksatz: Der Analyst beweist die Ursache über den Change-Record, nicht über Bauchgefühl. Die Hoheit über die Test-Suite bleibt beim Menschen.
QA Agent Blueprint08 · Analysis
Beispiel erzählen: Produkt ändert absichtlich ein Label, der alte Spec wird rot. Ohne Analyst: Bug-Ticket, Reopen, Ping-Pong. Mit Analyst: Change-Record zeigt die absichtliche Änderung → NEEDS_REVIEW mit Test-Vorschlag, Mensch entscheidet. Das ist der Unterschied zwischen Bug-Lärm und Signal.
Spotlight 4 · das Kernstück

Der Verdict Court — kein Rubber-Stamp-PASS

Vor jedem JIRA-Report tagt ein adversariales Gericht aus drei read-only Agenten in frischen Kontexten.

Prosecutor (Ankläger)

Argumentiert, warum das Verdict unsupported ist: fehlende Artefakte, nie ausgeführte Schritte, falsche Grün-Assertionen, verwässerte Akzeptanzkriterien. Jeder Angriff zitiert konkrete Evidence.

Defender (Verteidiger)

Belegt jedes Akzeptanzkriterium mit konkreten Artefakten: ausgeführter Run, bestandener Red-Check, Assertionen die wirklich prüfen. Widerlegt wahrscheinliche Angriffe — mit Zitaten.

Judge (Richter)

Unabhängig — nicht der Orchestrator, nicht der Executor. Prüft die Zitate gegen die echten Dateien und fällt das Urteil: supported / unsupported / needs-human.

OEV — die gemeinsame Checkliste

ObservableGibt es ein echtes Artefakt pro behauptetem Schritt?
ExecutableWurde die Erwartung wirklich ausgeführt (Run, Spec, Red-Check)?
VerifiablePrüfen die Assertionen die ACs bedeutungsvoll — positiv, spezifisch?
Grounding-Regel: Auch die Richter sind LLMs und können fabrizieren. Jede Behauptung — Angriff wie Verteidigung — muss eine konkrete Evidence-Stelle zitieren. Ohne Zitat: Rauschen.
QA Agent Blueprint09 · Verdict Court
Hier die meiste Sprechzeit einplanen. Analogie: vier-Augen-Prinzip, das mechanisch immer stattfindet — nicht nur wenn jemand Zeit hat. Der mechanische Validator bleibt Ground Truth für „ist etwas passiert"; der Court streitet über die Bedeutung. Beispiel false-green: eine negative Assertion („kein Fehler sichtbar"), die grün ist, weil gar nichts geladen wurde.
Kostenkontrolle · zwei Achsen

Zwei Achsen, nicht eine: Mode ≠ Lane

Execution Mode = wer den Browser steuert. Modell-Lane = welches Modell-Budget die Rolle bekommt. Beides wird unabhängig gewählt.

Execution Mode (pro Projekt)

mcp-onlyModell steuert Browser live — tiefste Findings, höchste Kosten
hybridDefault: Recon-Probe + Spec per CLI + kurzer Live-Check
cli-firstnur Suite; MCP bei unklarem Fehler — CI-günstig

Eskalation (visuelles Ticket, hohes Risiko, unklare Assertion) hebt jeden Mode auf Live-Beobachtung. Der Mode steht im JIRA-Report: beobachtet vs. nur asserted.

Modell-Lane (pro Branch, nach Risiko)

cheapschnell / niedriges Risiko
standardkomplex, niedrig–mittel · auch bei „unklar"
deephohes Risiko / eskaliert

Executor und Automator existieren in jeder Lane. Der Automator ist zusätzlich ~4× günstiger als derselbe Flow im MCP-Loop.

Fürs Budget: Risiko entscheidet die Modell-Tiefe, Wiederholbarkeit entscheidet CLI statt Live-Browser. Zwei Stellschrauben statt einer Pauschale.
QA Agent Blueprint10 · Modes & Lanes
Diese Slide bewusst gegen die häufigste Verwechslung gebaut: „deep" ist kein Browser-Modus, sondern ein Modell-Tier; „mcp-only" ist kein teures Modell, sondern Live-Steuerung. Beispiel: tiefes Risiko + wiederholbarer Flow = deep-Lane-Automator per CLI. Das ist die Kostenkontrolle, die QA-Leads lieben.
Sicherheitsgrenzen

Guards: was der Agent nicht darf

Secret-Schutz: Werte nie im Kontext

  • 1. Runner-Injection: Agent nennt nur Keys (STAGE_USER); der Runner lädt Werte selbst und redacted jede Ausgabe.
  • 2. MCP-Maskierung: Playwright-Server löst Werte serverseitig auf und maskiert sie in jeder Antwort.
  • 3. Direct Read: nur wenn ein Mensch secrets_read: allow setzt — Writes, Kopien, sed -i, rm bleiben trotzdem blockiert.

Keine Self-Privilege-Escalation

Der Guard verweigert Agent-Schreibzugriffe auf die Guard-Konfiguration .qa-guard.json selbst. Ein Agent, der den Toggle editieren kann, kann sich selbst Zugang gewähren — der Toggle wäre Theater. Umschalten ist Menschen-Aufgabe.

Fail closed

Interpreter-Einzeiler, ungültige Config, fehlende Datei → block. Im Zweifel nie „lesen".

Shadow Mode: ON by default

Der Agent komponiert JIRA-Kommentare und Reports, postet aber nichts, bis der Mensch Shadow mode: off schreibt. Der PreToolUse-Guard erzwingt das für alle Atlassian-Schreiboperationen. Die Freigabe bleibt beim Menschen.

QA Agent Blueprint11 · Guards
Für das Kunden-QA-Team der wichtigste Vertrauens-Slide: kein unkontrollierter Schreibzugriff aufs JIRA, keine Secrets im Transcript, keine Selbst-Ermächtigung. Alles mechanisch durchgesetzt, nicht als Bitte im Prompt. Frage ans Team: „Wer dürfte bei euch JIRA-Transitionen auslösen?" — Antwort: erst der Mensch nach Freigabe.
Enforcement

Rules sind Prosa — Hooks sind Enforcement

Vier Hooks entlang des Session-Lebenszyklus setzen durch, was Regeln nur empfehlen.

SessionStart

Orientierung: Projekte, Router, Secrets aus der Keychain. Meldet ungroomte Learnings — kein stiller Backlog.

PreToolUse

Guard vor jeder Aktion: blockt Secret-Writes, schützt die Guard-Config, erzwingt das Shadow-Gate für JIRA.

PostToolUse

Append-only Audit-Log jeder JIRA-Schreibaktion — auch in headless/CI-Läufen. Lückenlose Nachvollziehbarkeit.

Stop

Blockiert das Session-Ende, wenn Evidence oder die Learnings-Deklaration fehlt. Kein „hab getestet, trust me".

Prinzip P5: advisory rules + mechanische Garantien. Ein Prompt kann vergessen werden — ein Hook nicht.
QA Agent Blueprint12 · Hooks
Lebenszyklus einmal laut durchgehen: Start → vor jeder Aktion → nach jeder JIRA-Aktion → am Ende. Der Stop-Hook ist der Lieblingshook aller QA-Leads: Session darf nicht enden, ohne dass execution_summary.json Existenz und Learnings deklariert. Audit-Log beantwortet die Compliance-Frage „was hat der Agent in unserem JIRA getan?".
Learning Loop

„Einmal erklären, nie wieder"

Wissen gilt erst als gelernt, wenn es in einer Rule oder PROJECT.md steht — automatisch geladen, reviewbar im Merge Request.

Capture

Jede Session: nur echt neue Findings in den Inbox (memory/learnings/_inbox.md), mit Kandidaten-Ziel. Agent-Fehler bekommen vorher eine 5-Whys-RCA.

→

Groom

Wöchentlich: Dedupe, seen:-Counter, stale Einträge werden retired. Ein Batch oldest-first.

→

Promote

Gate: ≥ 2 Sessions. Dann Merge in Rules, Skills oder Projektkontext — validierungs-gegated über Evals.

Team-geteilt in Git — bewusst kein Memory-Server

  • Lokale DBs isolieren Wissen pro Laptop — genau die Wiederholung, die der Blueprint beseitigt.
  • Ein Recall-Server nimmt den Druck zu promoten; Git erzwingt Review und Teilung.
  • Korpus ist Plain Text: jeder Memory-Server kann ihn später ingesten.
Mechanisch verankert: Stop-Hook blockiert ohne Learnings-Deklaration; SessionStart meldet den Inbox-Backlog. Beide Enden der Pipeline sind erzwungen, nicht optional.
QA Agent Blueprint13 · Memory
Unterschied Recall vs. Promotion erklären: ein durchsuchbarer Haufen alter Notizen ist kein gelerntes Wissen. Gelernt = steht in der Datei, die der Agent ohnehin liest, und ist im MR reviewbar. Fürs Team: eure Learnings landen in Git, nicht auf einer Laptop-DB — Kollegen profitieren ab dem Merge.

Setup & Lifecycle

Onboarding: Wissen, das bleibt — und Updates, die nicht wehtun

/onboard-project

einmalig · ~30–60 min Interview

  • Füllt PROJECT.md Sektion für Sektion: JIRA-Key, Deployment (Cloud/DC), Zugriff (mcp/browser), Stage-URL + Versionscheck, Testuser als Vault-Keys, Deploy-Runbook, Readiness + Merge-Policy.
  • Report-Format wird aus JIRA geholt, nicht geraten. Seeds: learnings.md, Bug-Template, memory/INDEX.md.
  • Grundregel: nie den Prozess eines Projekts raten.

/onboard-product

pro Produkt · 5–15 min, nur Delta

  • products/<PRODUCT>/PRODUCT.md erbt alles vom Projekt; jede Frage lautet „gleich oder anders?" — „gleich" schreibt nichts.
  • Routing: JIRA-Component/Label → Produkt; echte Component-Liste wird per MCP geholt. Registry steht nur in PROJECT.md.
  • Feature-/Testmethoden-Matrix: immer gefragt, nie vererbt — zahlt sich auf jedem späteren Ticket aus.
  • Erstes Produkt ⇒ Routing-Pflicht: Produkt oder project-wide (explizites Ja).

/re-board <KEY>

nach Blueprint-Updates · ~10 min

  • Schema-Delta statt Neu-Interview: fehlende Felder (z. B. Execution Mode, Evidence Retention), fehlende flow-map.md (Seed mit Evidence-Gate), offene TODOs, Versions-Lücke + relevante CHANGELOG-Einträge (/whats-new rendert voll).
  • Zwei read-only Audits: Hygiene (Größe, Duplikate, Widersprüche, Provenienz) + Harness-Delta (MCP-Contract, Secrets-Wiring).
  • Jede Änderung einzeln bestätigt, dann Versions-Stempel neu. Kein Projekt wird zum Re-Onboarding gezwungen.
Warum das fürs Team zählt: Das Interview passiert einmal; das Wissen liegt versioniert in Git und wird automatisch geladen. Updates bleiben billig — genau deshalb aktualisieren Teams überhaupt.
QA Agent Blueprint15 · Onboarding & Lifecycle
Drei Lebenszyklus-Momente: neues Projekt (Interview, einmalig), neues Produkt im Projekt (Delta, Minuten), Blueprint-Update (re-board, Delta mit Einzelbestätigung). Preflight — der Umgebungs-Türsteher

  • Alle Stage-/Umgebungs-URLs antworten (auch 401 = erreichbar), JIRA-Base-URL antwortet.
  • VPN-Posture: zwei verbundene VPNs = FAIL (Routing-/DNS-Kollision); vergessenes VPN fällt als unerreichbare URL auf.
  • Deklarierte Secret-Keys vorhanden — nur Namen, nie Werte.
  • Pass → ok.json; das PreToolUse-Gate blockt MCP-Calls ohne frischen Pass (TTL 60 min). FAIL löscht den Pass wieder.

Readiness — der Ticket-Türsteher

  • Erlaubter JIRA-Status, keine Blocker.
  • Verlinkter MR/PR merged, erwarteter Build deployed (API/CLI bevorzugt).
  • Fehlender Merge/Build → BLOCKED, nicht „trotzdem testen".
  • Erst danach: Stage-Liveness, Recon, Execution.

Deep Cuts I · die Beweis-Maschine

Cool stuff: Gates, die man lesen und ausführen kann

Evidence, die man prüfen kann

  • Schema-v2-Validator: Pfade, Coverage, Outcomes, Artifact-SHA-256 — nicht nur „Datei existiert".
  • Normalizer vereinheitlicht Playwright- und WDIO-Results.
  • Historische Evidence wird nie umgeschrieben; Kompression trifft nur die Modell-Kopie, Rohdaten bleiben immutabel.

Kontext, der nicht driftet

  • Versiegelte Context-Capsule mit Source-Hashes; Drift → STALE_CONTEXT statt stiller Neu-Merge.
  • Semantisches Journal aus der Recon: reproduzierbarer Start-State-Seed, automation-handoff.json — „ready" ist kein Verdict.
  • Keine Roh-Refs, keine Secrets im Journal.

Tests, die nicht lügen

  • Statischer Test-Code-Scanner: False-Green-Muster (skip/fixme-Semantik, negative Assertionen, leere Oracles) vor der Ausführung.
  • Locator-Healing nur als Kandidat: Negative Control muss fehlschlagen, Mensch wählt, Intent-Drift wird abgelehnt.
  • verify-sightings: „seen ≥ 2" wird über distinkte Runs gezählt — nicht selbst attestiert.
Muster: Jedes Gate ist ein Skript mit Fixture-Tests, keine Prosa im Prompt. Was der Agent behauptet, wird gegen Dateien geprüft — dieselbe Disziplin wie im Verdict Court.
QA Agent Blueprint17 · Deep Cuts I
Für QA-Engineers der spannendste Teil: der Blueprint wendet seine eigene OEV-Disziplin auf sich an. Beispiele nennen: ein Spec mit toBeVisible() auf einem leeren Container ist grün ohne Wert — der Scanner flaggt das. Healing ohne Negative Control wäre Roulette. Und der seen-Counter: derselbe Agent, der ein Learning captured, darf seinen eigenen Counter nicht einfach hochzählen — distinkte Runs müssen es belegen.
Deep Cuts II · Betrieb

Cool stuff: mehrere Sessions, ein Stage, kein Chaos

Stage-Leases & Namespacing

  • Parallele Läufe erzeugen Testdaten unter Run-Präfix — cheap, parallel-friendly.
  • Leases für alles, was nicht namespaced werden kann: Deploy, globaler Reset, Cache-Flush.
  • Adaptiv: ohne Coordination-Sektion läuft der Home im Solo-Modus — kein Overhead für Einzelplatz.

Retention & Rollup

  • Zweistufige Evidence-Retention: schwere Artefakte zuerst, ganze Runs später; Index vor Delete.
  • Prunen ist Menschen-Schritt — der Guard blockt Agent-Deletes.
  • Epic-/Release-Rollup klassifiziert Kinder und flaggt stale Builds: go/no-go gegen Gates, nicht gegen Hoffnung.

Ein Home, zwei Harnesses

  • QA-Home per Walk-up zum .qa-home-Marker — Sessions in Unterordnern duplizieren keine Daten.
  • Shared Mode + /agentswitch: Claude Code und opencode abwechselnd, read-only Switch-Check.
  • Flow-Map mit Provenienz (source:, basis:, confirmed Areas); Routing lernt aus Korrekturen.
Warum das zählt: Sobald zwei Menschen oder zwei Sessions auf derselben Stage testen, zerstören sie sich sonst gegenseitig die Testdaten. Leases + Namespacing machen Parallelbetrieb sicher — und Retention hält die Evidence lesbar, ohne Beweise zu vernichten.
QA Agent Blueprint18 · Deep Cuts II
Anschluss an den Team-Alltag: „Wer von euch teilt sich eine Stage?" Leases erklären wie ein Mutex für Deploy/Reset. Retention: der Agent plant und benachrichtigt, löschen darf nur der Mensch — gleiche Philosophie wie Shadow Mode. Rollup: ein Epic ist nicht „getestet", weil drei Kinder grün sind — stale Builds und untestete Kinder werden explizit benannt.
Quality Gate · wir testen den Agenten selbst

Der Blueprint hält sich an seine eigenen Regeln

Dieselbe Evidence-Disziplin, die er vom Test verlangt, gilt für jede Änderung an ihm selbst.

Fixture-Batterie

  • 31 Test-Skripte für Hooks, Guards, Secrets, Capsule, Leases, Retention, Healing, Scanner, Installer (Wizard, opencode, shared, integrate) + Context-Budget.
  • Jede Änderung am Harness läuft die Batterie — „within budget" + alle Fixtures grün.

Behavioral Evals (~70 Cases)

  • Norm → Case-Matrix (evals/COVERAGE.md): jede geänderte Norm hat einen Test.
  • Frischer Judge plus deterministische Artefakt-Checks: Hash-Diffs, SHA-256, Browser-Events, Canary-Leaks. Artefakt-FAIL schlägt Judge-PASS.
  • Gate ≥ 0.9 über 3 Runs; Honesty-Cases (Hollow-PASS, Secret-Leak-Canary); --baseline gegen das nackte Modell.

Release-Disziplin

  • Manifest-/Versions-Abgleich, SemVer-Tags, Runtime-Smoke mit echter CLI.
  • Update-Smoke-Test vor dem Tag: vorherige Release installieren, updaten, Inventar prüfen — der 0.2.0-Duplicate-Hooks-Bug trat nur beim Update auf, nie frisch.
  • Promotion von Rules/Skills ist eval-gegated; Kosten-Disziplin: Evals strip MCP, Browser nur gepinntes Playwright.
Merksatz: Wir testen den Tester. Ein QA-Harness, der seine eigenen Regeln nicht mechanisch prüft, wäre genau das Rubber-Stamp-Problem, das er lösen soll.
QA Agent Blueprint19 · Quality Gate
Abschluss-Vertrauensanker: die ~70 Cases sind keine Demo-Tests, sondern Regression gegen Normen — z. B. shadow-mode, preflight-gate, verdict-court-hollow-pass, healer-requires-valid-negative-control. Deterministische Checks überstimmen den Judge: Prosa kann überzeugend klingen und trotzdem FAIL sein. Das ist OEV auf den Blueprint selbst angewendet. Auf Fragen vorbereiten: „Was kostet das?" — Kosten-Disziplin: nur betroffene Cases during development, volle Gate pre-release.
Fazit

Was das QA-Team davon hat

Skalierbare Verifikation

Mehr KI-Code, ohne die Kontrollinstanz abzugeben: Evidence, Court und Audit laufen mechanisch mit — nicht nur wenn jemand Zeit hat.

Weniger Bug-Ping-Pong

Triage trennt echte Defekte von veralteten Tests, bevor ein Ticket filed wird. NEEDS_REVIEW statt Reopen-Schleife.

Team-Wissen statt Chat-Wissen

Learnings in Git, reviewbar, automatisch geladen. Neue Kollegen erben die Stolperfallen des Teams.

Ehrlicher Status: Alpha. Gegen Fixtures und ein fiktives Referenzprojekt getestet; noch keine Validierung im Realbetrieb. APIs und Formate können sich zwischen Releases ändern. Einladung zum Pilot: benutzen, kaputt machen, Feedback geben.
QA Agent Blueprint20 · Nutzen & Status
Nutzen in der Sprache des Teams: Kontrolle, weniger Ticket-Lärm, geteiltes Wissen. Alpha nicht verstecken — als Pilot-Einladung framen: genau deshalb ist ein QA-Team als früher Nutzer wertvoll. Erwartung managen: Formate können sich ändern.
