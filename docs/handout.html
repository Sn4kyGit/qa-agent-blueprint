QA Agent Blueprint

JIRA-Ticket rein, getestetes Ticket raus — mit Evidence-Pflicht, adversarialem Verdict Court und Learning Loop. Ein äußeres QA-Harness über Claude Code oder opencode.

35 Skills12 Subagenten4 Hooks2 MCP-ServerStatus: Alpha

01Was es ist — und was nicht

Ein Agent besteht aus Modell + Harness. Claude Code und opencode sind innere Harnesses: sie führen das Modell aus. Der Blueprint ist das äußere QA-Harness darüber: er führt keinen Modell-Loop aus, sondern macht die Ausführung vertrauenswürdig und überprüfbar. Harness-agnostisch, modell-agnostisch.

Drei Zusagen, die mechanisch durchgesetzt werden: Evidence (maschinenlesbare Testbeweise, validiert statt behauptet), Verdict Court (drei unabhängige Agenten prüfen jedes Urteil vor dem JIRA-Report), Learning Loop (Wissen wird team-geteilt in Git versioniert und automatisch geladen).

Abgrenzung: Kein Test-Tool und kein Modell. Es orchestriert vorhandene Werkzeuge (Playwright, CLI-Suites, JIRA) unter QA-Disziplin.

Modell-Lanes (cheap / standard / deep) werden pro Execution-Branch nach Risiko gewählt: schnell/niedrig → cheap; komplex niedrig–mittel → standard; hoch/eskaliert → deep; unklar → standard. Fast Path: testbar + niedriges Risiko + keine Eskalation + ein Branch → direkt an einen cheap-Agenten, ohne QA-Manager.

Nicht verwechseln: Execution Mode (mcp-only / hybrid / cli-first) bestimmt, wer den Browser steuert; die Modell-Lane bestimmt das Modell-Budget. Beide Achsen sind unabhängig. Der Mode steht in jedem JIRA-Report: beobachtet vs. nur asserted.

04Der Verdict Court & OEV

Vor jedem Report tagt das Gericht aus drei read-only Agenten (keine Writes, keine Delegation, kein Browser, kein JIRA-Write). Prosecutor und Defender dürfen parallel laufen; der Judge folgt mit beiden Briefs. Gemeinsame Checkliste:

AchseFrageFalse-Green, das sie fängt
ObservableEchtes Artefakt pro behauptetem Schritt?Summary-Behauptung ohne Screenshot/Log/Trace
ExecutableErwartung wirklich ausgeführt (Run, Spec, Red-Check)?„hätte getestet"; Spec, der nie rot war
VerifiableAssertionen prüfen die ACs bedeutungsvoll — positiv, spezifisch?negative Assertion grün; AC verwässert zu toBeVisible()

Grounding-Regel: Auch Richter sind LLMs und können fabrizieren. Jede Behauptung muss eine konkrete Evidence-Stelle zitieren (Artefakt-Pfad, TC-ID, AC-Nummer); ohne Zitat ist sie Rauschen. Der mechanische Validator bleibt Ground Truth für „ist etwas passiert" — der Court streitet über die Bedeutung.

05Guards & Shadow Mode

  • Secret-Schutz, drei Stufen: (1) Runner-Injection — Agent nennt nur Keys, Runner lädt Werte selbst und redacted jede Ausgabe; (2) MCP-Maskierung serverseitig; (3) Direct Read nur nach menschlichem Opt-in (secrets_read: allow in .qa-guard.json).
  • Auch im Allow-Modus blockiert: Writes/Edits/Redirects auf .env*, cp/mv, sed -i, rm, Interpreter-Einzeiler (fail closed).
  • Keine Self-Privilege-Escalation: Agent-Schreibzugriffe auf .qa-guard.json werden verweigert — sonst könnte sich der Agent selbst Zugang gewähren.
  • Shadow Mode ON by default: JIRA-Kommentare/Reports werden komponiert, aber nichts gepostet, bis der Mensch Shadow mode: off setzt (oder QA_AGENT_SHADOW=0). Mechanisch erzwungen für alle Atlassian-Writes.
  • Secrets nie in Chat, Memory oder Evidence — nur Referenzen. Key-Konvention: <ENV>_*, SHARED_*, OWNER_*.

Prinzip: Rules sind Prosa (advisory), Hooks sind Enforcement (mechanisch). Ein Prompt kann vergessen werden — ein Hook nicht.

07Memory & Learning Loop

Capture (jede Session, nur neue Findings in memory/learnings/_inbox.md; Agent-Fehler mit 5-Whys-RCA) → Groom (wöchentlich: Dedupe, seen-Counter, retire) → Promote (Gate ≥ 2 Sessions: Merge in Rules/Skills/Projektkontext, eval-validiert). Flow-Wissen promotet in flow-map.md.

Bewusst kein externer Memory-Server: lokale DBs isolieren Wissen pro Maschine, sind nicht reviewbar und nehmen den Druck zu promoten. Git ist team-geteilt, versioniert, diffbar — sobald das Team committet. Ebene 2 (persönliche Auto-Memory) ist nur Kurzzeit-Puffer; bei Konflikt gewinnt das Repo.

Ehrliche Grenze: Der Blueprint committet und pusht nicht selbst — kein Hook und kein Skill führt Git-Operationen aus. Capture/Groom/Promote schreiben Dateien in den Working Tree; Commit, Push und Merge-Request-Review sind Menschen-/Team-Schritte (das Review-Gate bleibt bewusst erhalten). Ein QA-Home darf sogar unversioniert sein (AGENTS.md); dann bleibt Wissen lokal — die Isolation, die der Blueprint Memory-Servern vorwerfen würde. Empfehlung: QA Home versionieren und Promotion-Commits wie Code reviewen, z. B. im festen Rhythmus nach dem Grooming.

08Skills & Ticket-Flow

Kern: /test-ticket · /retest-bug · /report-to-jira. Analyse: /failure-analysis · /bug-report · /bug-reproduction. Test-Arten: /exploratory-testing · /test-automation · /recon · /security-testing · /accessibility-testing · /visual-testing · /api-testing · /test-reliability. Planung/Reporting: /risk-based-testing · /qa-report · /rollup · /release-readiness. Setup/Pflege: /onboard-project · /scaffold-suite · /retro-learn · /evidence-retention · /skill-review. Vollständige Übersicht: /qa-help.

Pipeline: Preflight (Umgebungs-Gate) → Intake → Routing (PROJECT.md, ggf. PRODUCT.md) → Readiness (Ticket-Gate: Status, Blocker, MR merged, Build deployed; sonst BLOCKED) → Strategie (Mode + Lane, Capsule versiegelt) → Execution → Evidence (Schema-v2, validiert) → Court → Report (Shadow-Gate).

Preflight — bevor Browser oder JIRA angefasst werden

  • Checks (Source of Truth: PROJECT.md): jede URL der Environments-Tabelle antwortet (curl; jeder HTTP-Status zählt, auch 401/403 = Host erreichbar); deklarierte JIRA-Base-URL antwortet; VPN-Posture (macOS): mehr als ein verbundener VPN-Dienst = FAIL (zwei VPNs kollidieren auf Routen/DNS; Override QA_PREFLIGHT_ALLOW_MULTI_VPN=1); deklarierte Keychain-Secrets vorhanden (nur Namen).
  • Mechanisch verankert: voller Pass schreibt evidence/.preflight/ok.json; das PreToolUse-Gate verweigert Playwright-/Atlassian-MCP-Calls ohne frisches Artefakt (TTL QA_PREFLIGHT_TTL_MIN, Default 60). Ein FAILED-Lauf entfernt das Artefakt — das Gate schließt wieder, statt auf einem alten Pass zu reiten. Escape-Hatch: QA_PREFLIGHT=0.
  • MCP-Liveness probe-t das Skript nicht (bash kann keine MCP-Server rufen); die Agent-Norm (QA-Manager Step 0) macht je einen trivialen Call pro Server.
  • Warum: die klassische False-Positive-Fabrik ist das vergessene VPN — Stage/JIRA unerreichbar, der Agent läuft in konfuse Errors, und das „Ergebnis" beschreibt die Umgebung, nicht das Produkt.
PASSFAILBLOCKEDNEEDS_REVIEW

PASS → Kommentar + finaler Screenshot + Transition „Verify". FAIL → Triage: Defekt → Bug („Reopen"); veralteter/brittle Test → NEEDS_REVIEW (Vorschlag, kein Bug); Environment → BLOCKED; Flake → test-reliability.

09Onboarding & Lifecycle

/onboard-project — dem Agenten ein Projekt beibringen (einmalig, ~30–60 min)

  • Füllt projects/<KEY>/PROJECT.md Sektion für Sektion im Dialog: JIRA-Key, Deployment (cloud/datacenter → MCP-Backend + Auth + Report-Format), JIRA-Zugriff (mcp oder browser), Umgebungen (Stage-URL, Versionscheck, wer deployt), Testuser nur als Vault-Keys + Secrets-Quelle (keychain/env-file), Deploy-Runbook, Readiness-Status, Merge-Policy, Blocker-/Build-Queries.
  • Report-Format (Transition-Namen, Priority-Schema) wird aus JIRA geholt, nicht erfragt. Seeds: learnings.md, Bug-Report-Template, Eintrag in memory/INDEX.md.
  • Grundregel des Routers: nie den Prozess eines Projekts raten — jedes Feld zählt für späteres autonomes Testen.

/onboard-product — ein Produkt im Projekt (5–15 min, nur Delta)

  • products/<PRODUCT>/PRODUCT.md erbt vom Projekt; jede Frage lautet „gleich wie Projekt, oder anders?" — eine „gleich"-Antwort schreibt nichts. Vererbte Sektionen werden gelöscht.
  • Routing: JIRA-Components/Labels → Produkt; die echte Component-Liste wird per Atlassian MCP geholt (tote Routing-Zeilen sonst stiller Session-Verlust). Registry + Match-Reihenfolge stehen nur in PROJECT.md; Nicht-Produkt-Components werden project-wide.
  • Feature-/Testmethoden-Matrix: immer gefragt, nie vererbt — sie steuert später die Strategiewahl des QA-Managers.
  • Erstes Produkt im Projekt: explizites Ja zur Folge „jedes Ticket routet ab jetzt zu Produkt oder project-wide".

/re-board <KEY> — Upgrade ohne Neu-Interview (~10 min)

  • Schema-Delta gegen aktuelles Template: fehlende Felder (z. B. Execution Mode, Evidence Retention — optional mit Defaults), fehlende Dateien (flow-map.md-Seed nur mit Evidence-Gate: Anchor braucht recon.json/verifizierte Spec-Schritte/menschliche Bestätigung), offene TODO:-Einträge, Versions-Lücke + relevante CHANGELOG-Einträge (/whats-new rendert die volle Übersicht).
  • Zwei read-only Audits: Hygiene (Größe/Hot-Context-Budget, Duplikate, Widersprüche, volatile Tickets in durable-Dateien, Flow-Map-Provenienz) und Harness-Delta (Playwright-Contract-Flags, Secrets-Wiring, legacy Atlassian-URLs).
  • Jede Änderung wird einzeln bestätigt; danach Bridge-File + Versions-Stempel aktualisiert. Konsolidierungen nie auf Kosten offener Fragen.
Warum: Das Interview passiert einmal, das Wissen liegt versioniert in Git. Updates kosten Minuten statt einer Stunde — genau deshalb aktualisieren Teams überhaupt. Verwandt: /scaffold-suite (fehlendes Playwright-Projekt), /whats-new (Changelog seit Onboarding), /agentswitch (Harness-Wechsel read-only prüfen).

10Deep Cuts: Beweis-Maschine & Betrieb

Gates als Skripte (nicht als Prosa)

  • validate-evidence.py + Schema-v2: Pfade, Coverage, Outcomes, Artifact-SHA-256; normalize-test-results.py vereinheitlicht Playwright/WDIO. Historische Evidence wird nie umgeschrieben; compress-tool-output.py komprimiert nur die Modell-Kopie (lossless-first), Rohdaten bleiben immutabel.
  • context-capsule.py: versiegelte Capsule mit Source-Hashes, Binding-Validate, STALE_CONTEXT bei Drift. action-journal.py: semantisches Journal aus der Recon mit reproduzierbarem Start-State-Seed und automation-handoff.json (Readiness ist kein Verdict); keine Roh-Refs/Secrets im Journal.
  • qa-test-code-scan.mjs: statischer Scanner für False-Green-Muster (skip/fixme-Semantik, negative Assertionen, leere Oracles) — test:quality. healing-candidate.py: Locator-Healing nur als Kandidat; Negative Control muss fehlschlagen; Mensch wählt; Intent-Drift abgelehnt.
  • verify-sightings.py: das seen: 2-Promotion-Gate wird über distinkte Runs (verschiedene execution_summary.json) gezählt — mechanisch statt selbst attestiert.

Mehrere Sessions, ein Stage

  • stage-lease.py: Run-Namespacing für Testdaten + Leases für Deploy, globalen Reset, Cache-Flush (optional grobes Stage-Write-Lease). Adaptiv: fehlende Coordination-Sektion ⇒ Solo-Modus.
  • evidence-retention.py: zweistufige Retention (schwere Artefakte zuerst, ganze Runs später), Index vor Delete, Protection-Regeln; Prunen nur durch Menschen. epic-rollup.py: Epic-/Release-Klassifikation mit Stale-Build-Flags und honest Coverage gegen Projekt-Gates.
  • QA-Home per Walk-up zum .qa-home-Marker (keine Daten-Duplikate in Unterordnern); Shared Mode + /agentswitch (read-only Switch-Check) für zwei Harnesses in einem Home. Flow-Map mit Provenienz (source:, Neighbor-basis:, confirmed Areas); Routing-Registry lernt aus Korrekturen.
  • model-setup.py: Consumer-eigene Lane-Overrides ohne Blueprint-Pinning; skill-review.py: Skill-Profile nur als Dry-run-Vorschlag, nie automatische Deaktivierung.

11Quality Gate: wir testen den Agenten selbst

  • Fixture-Batterie: 31 Test-Skripte unter .claude/hooks/tests/ (Guard, Preflight, Capsule, Secrets, Lease, Retention, Healing, Scanner, Rollup, Installer-Wizard/opencode/shared/integrate, Manifest- und Release-Conventions) plus Context-Budget-Check. Jede Harness-Änderung läuft die Batterie.
  • Behavioral Evals (~70 Cases): je Case prompt.md + graders/criteria.md + checks.json. Frischer Judge bewertet Antworten; deterministische Checks prüfen Workspace-Hash-Diffs (created/modified/deleted), Datei-Bytes, JSON-Pointer, Schema-v2-Felder, Artifact-SHA-256, Browser-Tool-Events, externe Navigation und Synthetic-Canary-Leaks. Ein Artefakt-FAIL ist ein FAIL, auch wenn Judge und Prosa bestehen. Hard-Gate ≥ 0.9, Variance ≥ 0.66, --runs 3 als Reliability-Gate; --baseline zeigt Verhalten des nackten Modells. Honesty-Cases u. a. verdict-court-hollow-pass, browser-no-secret-leak, perf-analysis-honesty.
  • Norm→Test-Matrix: evals/COVERAGE.md mappt jede Norm auf Cases; Norm-Änderungen erfordern Matrix-Update + Lauf der betroffenen Cases; volle Gate ist Pre-Release-Schritt. Kosten-Disziplin: Standard-Evals strip MCP, Browser-Sessions nur gepinntes Playwright; OpenRouter-Billing-Option.
  • Release-Disziplin: Versions-Abgleich Plugin/Marketplace, SemVer-Tags, plugin-runtime-smoke.sh mit echter CLI; Update-Smoke-Test vor dem Tag (vorherige Release installieren → updaten → Inventar prüfen; der 0.2.0-Duplicate-Hooks-Bug trat nur auf Update+Restart auf). Promotion von Blueprint-Rules/Skills ist eval-gegated.
Prinzip: Dieselbe Disziplin wie im Verdict Court — deterministische Artefakt-Checks überstimmen den LLM-Judge. Der Blueprint wendet OEV auf sich selbst an: „Wir testen den Tester."
