# QA Agent Blueprint — Harness & UX Audit (2026-09-18)

Audited against four dimensions the maintainer asked about: optimization for
**Claude Code**, optimization for **opencode**, general-purpose **LLM
reliability** (routing, ambiguity, token discipline), and **ease of install /
day-one handling** for a new user. Scope was the full repo at commit-tip
(`0.6.2`, with the uncommitted working-tree diff at audit time included).

Three independent passes were run in parallel, each reading its area in full
rather than skimming: Claude Code layer (`.claude/`, `.claude-plugin/`,
`CLAUDE.md`), opencode layer (`opencode/`, cross-checked against its Claude
Code counterpart file-by-file), and install/onboarding UX (`README.md`,
`install.sh`, `docs/quickstart-*.md`, `AGENTS.md`, `CHANGELOG.md`). Findings
below are merged, de-duplicated, and ordered most-severe-first within each
section. Every finding includes a concrete fix — not just "should be improved".

## A. Correctness / security-reliability risks

### 1. Shadow Mode has no mechanical enforcement

**Where:** `.claude/settings.json:45-55` (`PreToolUse` block), `.claude/hooks/pre-tool-guard.sh`, `.claude/rules/core/security.md`

**Problem:** `CLAUDE.md` and `security.md` both claim Shadow Mode is "enforced
by rule AND by hooks". In reality, `PreToolUse`'s only matcher is
`Bash|Write|Edit|MultiEdit|NotebookEdit` — it never fires for
`mcp__atlassian__*` tools. The only hook that touches Atlassian writes is
`post-jira-audit.sh`, wired to `PostToolUse`, which **logs after the write
already happened**. `security.md` itself says "a line in jira-writes.log from
a shadow run is a bug" — the design detects the violation, it does not
prevent it. An agent that is confused, or a ticket description that contains
a prompt-injection payload, can call the JIRA write tool directly while
Shadow Mode is on, and nothing in the hook chain stops it.

**Impact:** This is the single biggest gap between what the docs promise
("enforced by hooks, not goodwill") and what is actually wired up — and it's
exactly the control the rest of the security model leans on.

**Recommended fix:**

1. Add a second `PreToolUse` entry in `.claude/settings.json`, reusing the
   same matcher already proven correct in the existing `PostToolUse` block:

   ```json
   {
     "matcher": "mcp__.*atlassian__.*(create|edit|add|transition|update|delete).*",
     "hooks": [
       { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/pre-tool-guard.sh" }
     ]
   }
   ```

2. Extend `pre-tool-guard.sh` with a new check block (after the existing Bash
   checks, before `exit 0`):

   ```bash
   # 3. Never let a JIRA write through while Shadow Mode is on.
   if printf '%s' "$TOOL_NAME" | grep -qE '^mcp__.*atlassian__.*(create|edit|add|transition|update|delete)'; then
     if [ "${QA_AGENT_SHADOW:-1}" != "0" ]; then
       KEY="$(get_json 'import re; s=json.dumps(d.get("tool_input") or {}); m=re.search(r"[A-Z][A-Z0-9]+-[0-9]+", s); print(m.group(0) if m else "")')"
       PROJECT_KEY="${KEY%%-*}"
       SHADOW_OFF=0
       if [ -n "$PROJECT_KEY" ] && [ -f "projects/$PROJECT_KEY/PROJECT.md" ]; then
         grep -qiE 'shadow mode:\s*off' "projects/$PROJECT_KEY/PROJECT.md" && SHADOW_OFF=1
       fi
       if [ "$SHADOW_OFF" != "1" ]; then
         block "refusing a JIRA write — Shadow Mode is on (default). Compose to evidence/<KEY>/<TICKET>/<ts>/proposed-report.md instead. Unlock: QA_AGENT_SHADOW=0 or 'Shadow mode: off' in the project's PROJECT.md."
       fi
     fi
   fi
   ```

   This fails **safe**: if the ticket key can't be extracted or the project
   file can't be read, it stays blocked (shadow-on is the default posture
   already, so an unresolvable case should not silently open the gate).
3. Add matching fixtures to `.claude/hooks/tests/guard-fixtures.sh` — one case
   where `QA_AGENT_SHADOW` is unset and a JIRA write is blocked, one where
   `PROJECT.md` declares `Shadow mode: off` and the same call passes.
4. Port the identical rule to `opencode/plugins/qa-blueprint.ts` (see finding
   3 below for why this file needs to be treated as "must stay in lockstep",
   not an afterthought).

### 2. Stop-hook evidence check is not ticket-scoped

**Where:** `.claude/hooks/stop-evidence-check.sh:127-129` (`fresh_summaries()`)

**Problem:**

```bash
fresh_summaries() {
  find "$CWD/evidence" -name execution_summary.json -newermt '-2 hours' 2>/dev/null
}
```

This asks "does *any* `execution_summary.json` exist under `evidence/` from
the last two hours" — not "does one exist **for the ticket this session
actually worked**". In a realistic session ("test SHOP-1, now test SHOP-2"
within the same 2-hour window), a stale summary from SHOP-1 satisfies the
check even if SHOP-2 produced nothing. The hook reports "evidence exists"
when the evidence that matters doesn't.

**Impact:** The Stop hook is the mechanical backstop for the entire
"evidence is mandatory" promise — a false-negative here is a false-negative
in the one place the system can't tolerate one.

**Recommended fix:** The transcript-parsing Python block already inside
`looks_like_a_test_run()` walks every `tool_use` node — extend it to also
collect ticket keys, and check evidence per key instead of globally:

```python
# add near the top of the embedded Python, alongside the existing regexes
ticket_key_re = re.compile(r'\b([A-Z][A-Z0-9]+-[0-9]+)\b')

# inside walk(), wherever a tool_use node is inspected, also do:
#   for m in ticket_key_re.finditer(json.dumps(node)):
#       found_keys.add(m.group(1))
# and print(",".join(sorted(found_keys))) to stdout before sys.exit(...)
```

Then in bash:

```bash
TICKET_KEYS="$(looks_like_a_test_run_keys)"   # new function returning the csv from the python step
has_recent_evidence() {
  local key
  if [ -z "$TICKET_KEYS" ]; then
    fresh_summaries | grep -q .   # fallback: old global behavior if no key was extractable
    return
  fi
  for key in $(printf '%s' "$TICKET_KEYS" | tr ',' ' '); do
    find "$CWD/evidence" -path "*/$key/*/execution_summary.json" -newermt '-2 hours' 2>/dev/null | grep -q . || return 1
  done
  return 0
}
```

i.e. require a fresh summary **per ticket key seen in the transcript**, not
just one summary anywhere. Keep the existing untargeted check as the
fallback only when no key could be extracted at all (e.g. a session that
never touched JIRA), so the hook never becomes *stricter* than today in the
one case it can't disambiguate.

### 3. opencode guard message lags the Claude Code fix

**Where:** `opencode/plugins/qa-blueprint.ts:106` vs. `.claude/hooks/pre-tool-guard.sh:95`

**Problem:** The `0.6.2` changelog entry claims the improved `.env`-reader
guard message (pointing at `resolve-secrets.sh --status` as the sanctioned
way to check which keys exist) applies to "both harnesses". It was only
added on the Claude Code side:

```
# pre-tool-guard.sh:95
"...secrets never enter chat or context. To check which keys exist: resolve-secrets.sh --status."

# qa-blueprint.ts:106 (current)
block("refusing a command that reads/copies a .env* file — secrets never enter chat or context.")
```

Neither `guard-fixtures.sh` nor `opencode/tests/guard.test.ts` assert on
message *content* (only on block/allow), so this drifted silently.

**Recommended fix:** one-line change —

```ts
if (ENV_READER.test(noExample)) block("refusing a command that reads/copies a .env* file — secrets never enter chat or context. To check which keys exist: resolve-secrets.sh --status.")
```

Then add a message-content assertion to `guard.test.ts` for this case so the
next divergence fails CI instead of surviving to changelog time. This is the
concrete instance of a broader process gap: **the changelog should not claim
"both harnesses" for a change unless a shared fixture (or a script that diffs
the two guard files' constant strings) actually proves it** — see the
"process" note at the end of this document.

### 4. `pre-tool-guard.sh`'s secret-read protection is a keyword net, not a sandbox

**Where:** `.claude/hooks/pre-tool-guard.sh:94`, `.claude/rules/core/security.md`

**Problem:** The guard only intercepts a fixed command allowlist
(`cat|less|more|head|tail|cp|mv|grep|sed|awk|jq`). Anything else that reads a
file bypasses it untouched: `python3 -c "print(open('.env').read())"`,
`perl -pe`, `base64 < .env`, `xxd .env`, `dd if=.env`, or simply `source
.env` inside a heredoc. `security.md` states "No secrets in context, ever" —
phrased as an absolute guarantee, which this mechanism cannot deliver on its
own (a pure-regex Bash-argument guard structurally can't enumerate every way
to read a file).

**Recommended fix — two parts:**

1. **Be honest in the docs.** Add one sentence to `security.md` under
   "Secrets are references, never values": *"`pre-tool-guard.sh` blocks the
   common shell readers and the most obvious `.env` access patterns; it is a
   best-effort net, not a sandbox. The actual guarantee is defense in depth:
   MCP's `--secrets` substitution masks values at the browser layer
   regardless of what the agent tries to do with them afterward."* This
   matters because a reader who thinks the guard is airtight won't build the
   second layer of protection they'd otherwise reach for.
2. **Cheap coverage bump, not a full fix.** Extend the regex to catch the
   next-most-likely bypass class — interpreter one-liners — without chasing
   an unwinnable enumeration:

   ```bash
   if printf '%s' "$COMMAND_NO_EXAMPLE" | grep -qE '(python3?|perl|ruby|node|php)\b.*\.env([^a-zA-Z]|$)'; then
     block "refusing a command that appears to read a .env* file via an interpreter — secrets never enter chat or context. To check which keys exist: resolve-secrets.sh --status."
   fi
   ```

   Add fixtures for both the catch and a deliberate non-match (e.g. a Python
   command that only mentions ".env" in an unrelated string literal) so the
   false-positive rate stays visible.

## B. LLM routing / skill-description consistency

### 5. `webdriverio-testing` can be triggered directly, bypassing its orchestrator

**Where:** `.claude/skills/webdriverio-testing/SKILL.md:3-8` (frontmatter `description`)

**Problem:** The skill's own body says "Loaded by `test-automator` when
'Test assets' → Framework says webdriverio" — it's meant to be a sub-skill,
not a routing target. But its frontmatter description reads like a
standalone trigger ("Use when the project's or product's 'Test assets'
declare framework webdriverio"). If a user says "run the wdio suite for
SHOP-123", Claude Code's skill router could match this description directly
and skip `test-automation`'s scope resolution, evidence-dir setup, and TC-ID
assignment entirely.

**Recommended fix:** add an explicit non-trigger, matching the pattern
already used elsewhere in this repo (e.g. `test-ticket`'s "Not for
re-testing an already-fixed bug"):

```yaml
description: >-
  Write or run deterministic WebdriverIO specs (web, Selenium Grid remote, and mobile
  via Appium) through the WDIO CLI runner. Not for direct invocation — this is loaded
  by test-automation when a project's "Test assets" → Framework says webdriverio; route
  user requests to /test-automation instead. Not for Playwright suites — those follow
  docs/rules/testing/playwright-cli.md. Related: test-automation, test-reliability.
```

### 6. Inconsistent frontmatter pattern across native skills

**Where:** all `.claude/skills/*/SKILL.md`

**Problem:** The 10 vendored skills (`api-testing`, `accessibility-testing`,
`security-testing`, …) uniformly follow a "Use when X / Not for Y / Related
Z" template. Most native skills only state "Use for X" with no "Not for"
disambiguation: `bug-report`, `deploy-to-stage`, `qa-help`, `qa-report`,
`re-board`, `whats-new`, `onboard-product`, `onboard-project`,
`failure-analysis`, `report-to-jira`, `retro-learn`. (`test-ticket`,
`retest-bug`, `exploratory-testing` already do this correctly.) Since
routing correctness depends entirely on description text — there is no other
signal the model uses to disambiguate — the skills most likely to overlap in
practice are the ones missing the clause.

**Recommended fix:** apply a "Not for" clause to each of the eleven skills
above, naming the one skill it's most likely to be confused with. Concrete
starting point (adjust wording to match each skill's existing voice):

| Skill | Suggested "Not for" clause |
|---|---|
| `bug-report` | Not for triaging *why* a test failed — run `failure-analysis` first; this skill composes the ticket once the cause is known. |
| `deploy-to-stage` | Not for production deploys — this runbook only ever targets stage, and never runs unless `PROJECT.md` says the agent may trigger deploys. |
| `qa-help` | Not for testing a ticket — this only explains commands; route testing requests to `test-ticket`. |
| `qa-report` | Not for a single ticket's verdict — this aggregates across the evidence directory; a one-ticket result comes from `report-to-jira`. |
| `re-board` | Not for a brand-new project — that's `onboard-project`; this is the delta-upgrade path for an already-onboarded one. |
| `whats-new` | Not for applying changes — this is read-only; the apply step is always `re-board`. |
| `onboard-product` | Not for a project's first onboarding — that's `onboard-project`; this only adds a product inside an existing one. |
| `onboard-project` | Not for adding a product to an already-onboarded project — that's `onboard-product`. |
| `failure-analysis` | Not for filing the bug once cause is confirmed — that's `bug-report`, invoked after this skill's classification. |
| `report-to-jira` | Not for composing the bug ticket itself — that's `bug-report`; this only posts an already-produced verdict/comment. |
| `retro-learn` | Not for promoting a single learning mid-session — this is the session-end capture step; grooming/promotion is its own explicit pass. |

This is a text-only change, low risk, and directly reduces the chance of the
router picking a plausible-but-wrong skill.

### 7. `QA_AUDIT_USER` is an undocumented, opencode-only invention

**Where:** `opencode/plugins/qa-blueprint.ts:129`

**Problem:** The Claude Code side (`post-jira-audit.sh`) attributes audit-log
lines via `CLAUDE_USER_EMAIL` falling back to `$USER`. The opencode port
introduces a new env var, `QA_AUDIT_USER`, that appears nowhere else in the
repo (`grep -rl QA_AUDIT_USER` matches only this one file — not in `docs/`,
`security.md`, `AGENTS.md`, or either quickstart). An opencode user has no
way to discover this variable exists or what setting it does.

**Recommended fix:** either (a) drop it and fall back to `process.env.USER`
only, for genuine parity with the bash side, or — if opencode truly has no
equivalent of an authenticated user email worth capturing separately —
(b) keep it but document it in `docs/quickstart-opencode.md`'s prerequisites
table and in `.claude/rules/core/security.md`'s "Credential sources" section:
*"opencode has no equivalent of Claude Code's `CLAUDE_USER_EMAIL`; set
`QA_AUDIT_USER` if you want JIRA-write audit-log lines attributed to
something other than the OS `$USER`."* Option (a) is the lower-maintenance
choice unless there's a concrete reason opencode sessions need a distinct
identity from the OS user.

## C. Install & onboarding UX

### 8. README quickstart has five competing paths

**Where:** `README.md:70-175` ("Quickstart" section)

**Problem:** In reading order, a first-time visitor hits: (1) a
paste-this-prompt-to-your-agent flow, (2) a 2-command CLI flow, (3) an
opencode-specific variant of both, (4) a classic clone-and-run-`install.sh`
flow, (5) a manual `settings.json` edit — before reaching "First session"
(line ~174). The section header does say "Recommended mode: plugin", but
that's one sentence, not a structural signal; the reader still has to read
through four fully-formed alternative paths to find out none of them was
actually the default.

**Recommended fix:** restructure so exactly one path is visible by default:

```markdown
## Quickstart

**Recommended: plugin mode.** Nothing is copied into your project — rules,
skills, agents and hooks load from the plugin.

\```bash
claude plugin marketplace add Sn4kyGit/qa-agent-blueprint
claude plugin install --scope project qa-agent-blueprint@qa-agent-blueprint-marketplace
\```

Restart Claude Code, accept the trust dialog, then:

\```
/mcp                    # one-time: authorize "atlassian" (OAuth 2.1)
/onboard-project         # teach it your first project (~30–60 min, interactive)
\```

<details>
<summary>Other ways in — opencode, "tell your agent" prompt, clone + installer, manual settings.json, dry-run preview</summary>

… (existing four alternative blocks, unchanged, moved here) …

</details>
```

This keeps every existing path — nothing is removed — it just stops making
the reader choose between five options before they know what the tool does.

### 9. `install.sh`'s `--dry-run` is real, but buried

**Where:** `install.sh` (1,900 lines / 80KB), `README.md` Quickstart section

**Problem:** A single 1,900-line shell script that interactively rewrites
`.claude/settings.json`, `.mcp.json`, `.gitignore`, and `CLAUDE.md` is a
legitimate trust question for a new user, before they've read a line of it.
The mitigations are genuinely good — `--dry-run` prints the full plan without
touching anything, and `docs/integration.md` documents the detection matrix
and collision policy in detail — but `--dry-run` is never mentioned until
deep in the "classic way" block, after four other install paths.

**Recommended fix:**
1. Surface it in the priority slot: right under the single quickstart command
   block from finding 8, add: *"Preview everything the installer would do,
   without changing anything: `./install.sh --dry-run`."*
2. Longer-term (not urgent): split `install.sh` into a thin dispatcher plus
   `install/plugin.sh`, `install/integrate.sh`, `install/opencode.sh` sourcing
   a shared `install/lib.sh` — purely for auditability. 1,900 lines in one
   file is a lot to reason about even with the current good structure (39
   well-named functions); a mode-scoped split lets a cautious user read only
   the ~300-400 lines relevant to the path they're about to run.

### 11. Root-level file clutter hurts first impressions

**Where:** repo root — `overview.html` (43KB), `spickzettel-allgemein.{html,pdf}`,
`spickzettel-deepdive.{html,pdf}`, `spickzettel-technisch.{html,pdf}` (~1MB total)

**Problem:** Anyone landing on the GitHub repo root sees these six generated,
German-named files sitting next to `README.md`/`CLAUDE.md`/`AGENTS.md`. They
read as personal working artifacts that were accidentally committed rather
than deliverables — GitHub's root file listing is a first impression, and
this clutters it. (`overview.html` is linked from the README via GitHub
Pages, so it has a real reason to be web-reachable; the three `spickzettel-*`
pairs have no visible inbound link from README/docs at all.)

**Recommended fix:**
1. Move `overview.html` into `docs/` (or `docs/public/`) and update the
   GitHub Pages source setting (or the Pages workflow, if one exists) plus
   the README link accordingly — GitHub Pages can serve from `/docs` on the
   default branch just as well as from root.
2. For the three `spickzettel-*` pairs: confirm intent first. If they're
   meant to be public-facing cheat sheets, rename to English and move into
   `docs/` alongside `overview.html`. If they're personal working notes, they
   don't belong in the tracked tree at all — move them out of the repo (or
   into a `.gitignore`d local folder) rather than shipping them to every
   clone.

### 12. opencode quickstart doesn't mirror a caveat from the plugin quickstart

**Where:** `docs/quickstart-plugin.md` vs. `docs/quickstart-opencode.md`

**Problem:** The plugin quickstart has a "What is different without an app
repo" section (failure-analysis runs degraded, deploy-to-stage is
BLOCKED-by-design) with no equivalent in the opencode quickstart. The
behavior almost certainly applies identically under opencode — it's a
property of the ticket/repo relationship, not the harness — but an
opencode-only reader has no way to know to expect it.

**Recommended fix:** add a one-line cross-reference in
`docs/quickstart-opencode.md`: *"Same caveats apply as under the plugin
regarding tickets with no linked app repo — see
[quickstart-plugin.md § What is different without an app repo](quickstart-plugin.md#what-is-different-without-an-app-repo)."*
Cheaper than duplicating the section, and keeps a single source of truth.

## D. What's already solid (calibration, not findings)

These were checked and found genuinely correct — listed so the findings above
aren't read as "the whole thing is shaky":

- **Hooks are unusually well-documented for their own history.** Both
  `pre-tool-guard.sh` and `stop-evidence-check.sh` carry inline comments
  citing the actual regression each safeguard was added for (e.g. the
  2026-09-05 fail-open bug from a swallowed Python stderr, the field-reported
  `grep -o` bypass), and the fail-closed fallback (`if [ -z "$TOOL_NAME" ]` →
  scan the raw payload) is a correct, non-obvious design choice.
- **Rule tiering resolves cleanly.** Every cross-reference between
  `CLAUDE.md`, `product-layer.md`, `evidence-policy.md`, and `security.md`
  points at a real file/section — no dangling references found anywhere in
  the always-loaded tier.
- **Agent tool grants match stated responsibilities.** `failure-analyst`
  deliberately has no `Write`/`Edit` access, matching its "never applies a
  test change, only proposes" rule — a structural control, not just a prose
  one.
- **The opencode port is not bolted on.** `opencode/ROUTER.md` and root
  `CLAUDE.md` are near-identical by design, with deltas that are correct,
  deliberate harness adaptations (e.g. "Stop hook" → "the evidence gate").
  The evidence gate on opencode is actually a *proactive improvement* over
  the Claude Code side — it fires via `tool.execute.before`, blocking a JIRA
  write before it happens, rather than only at session end like the bash
  Stop hook (a reasoned adaptation to opencode having no exit-2/block-stop
  primitive, documented inline in `qa-blueprint.ts`).
- **The 11 skills with no opencode `commands/*.md` wrapper are intentional,
  not drift** — confirmed against `docs/opencode-port-plan.md`: only the
  ~16 entry-point skills get command wrappers on either harness; the
  vendored specialist skills are pulled in by `qa-manager`'s judgment on
  both sides alike.
- **This session's own uncommitted edit** (the "browser-driving subagents
  run sequentially" paragraph) is byte-identical between
  `.claude/agents/qa-manager.md` and `opencode/agents/qa-manager.md` —
  correctly mirrored, including the opencode frontmatter's `permission.task`
  allowlist staying scoped to the four leaf agents.
- **`onboard-project` and `qa-help` are the strongest part of the onboarding
  chain** — honest about time cost (30–60 min), never guesses at process,
  and point at a filled reference project (`projects/EXAMPLE/`).
- **`context-budget.sh` is a genuinely meaningful test**, not a superficial
  one — it measures the actual always-loaded tier and has real history
  entries justifying each budget raise. Its only open question (not
  confirmed either way in this audit) is whether it's wired into CI as a
  merge gate, or only run on demand.
- **CHANGELOG churn (three releases in ~2 days around the repo rename) reads
  as healthy fast iteration pre-1.0**, not instability — each release fixed
  a real, specific bug from the one before it, not a re-opened regression.

## Process note

Two of the findings above (3 and part of 7) exist because a change was made
on one harness and assumed — not verified — to apply to the other. The
underlying gap isn't any single line of code; it's that nothing currently
diffs the two guard implementations' user-facing strings against each other.
Worth considering, independent of the two immediate fixes: a small CI check
(or a `bun test` case) that extracts every `block(...)` message string from
both `pre-tool-guard.sh` and `qa-blueprint.ts` and asserts the sets match
1:1. That would have caught finding 3 automatically instead of requiring a
manual audit to notice.
